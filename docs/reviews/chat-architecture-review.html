最严重的一处 · 已证实

isRelevantToRole(text, a.Role)（main.go:397）用 map 的键是 「后端」「前端」「测试」「运维」「全栈」， 但它拿到的 a.Role 实际值是 "Go 专家，关注 API 设计、并发安全与查询效率"（src/lib/presets.ts:3）。 键永远不命中，函数恒返回 false。

后果：没 @ 任何人时，没有任何成员会回复；代码里的 「角色相关，选择性回复」 分支从未执行过。 用户看到的现象是「群里发消息没人理」，而日志显示「不相关，跳过」。

次严重 · 已证实

前端 insertMention（ChannelView.tsx:74）插入的是 @ + agent 的 name（如「前端」）； 后端解析后与 a.Name 比对 —— 这条对上了。但 parseMentions 用 strings.Fields 切词， 名字带空格就会断；Go 侧 parseMentions 和前端 filtered 和 insertMention 是三份互不相同的解析逻辑。

1 · 没有一个「频道投递」module：fan-out 逻辑全裸在 Sidecar 里

main.go:315 SendToChannel · main.go:378 parseMentions · main.go:397 isRelevantToRole

Strong in-process

Before · 决策逻辑散落三处

main.go · Sidecar

谁该回 · 拼 prompt · 收集 errs · 打日志

isRelevantToRole

硬编码关键词表 · 恒返回 false

parseMentions

Fields 切词 · 名字带空格即断

测试覆盖 0

After · 一个 deep module

Dispatch

Dispatch(channelId, msg) → []Delivery

· 提及解析（一份，前后端共用）

· 该谁回（显式规则，可测）

· 每人一份投递记录（成功/失败）

· prompt 组装（含群历史）

interface 1 个方法 测试 1 个 seam

Problem

「谁该回、回什么、失败了怎么办」三个决策全在 SendToChannel 的一个 for 循环里，和 I/O 搅在一起。任何一条规则改错都只有一个后果：群里静默无人回复，且没有测试能发现。

Solution

把 fan-out 决策抽成一个 deep module：入参是消息和成员，出参是「每个成员的投递计划」。Sidecar 只负责把计划交给 mgr.Prompt。提及解析只保留一份，前端复用同一份语义。

Wins

  • · leverage：一个 Dispatch 覆盖「谁回」全部规则
  • · locality：isRelevantToRole 的恒 false 类 bug 一处可测
  • · 提及解析从 3 份降到 1 份
  • · 投递结果成为数据，不再是一句拼起来的错误字符串

接口形状（定形，不写码）

type Delivery struct { AgentID, Prompt string; Reason string }

Dispatch(msg Message, members []Member) []Delivery
— Reason 用来解释「为什么回/不回」，
直接变成 UI 上的「为什么没人理我」

2 · agent 在群里看不见别的 agent 说了什么

main.go:360 prompt 构造 · channel.Messages 从不进入任何 Agent.Messages

Strong in-process

Before · 每个 agent 只看到「用户那一句」

After · transcript 是共享事实源

Problem

prompt 只有 [channel:X] 发言人: 正文 一句。频道的历史不进 prompt，别人的发言永远不出现。多个 agent 的「协作」实际上是在同一频道里各说各话，没有任何一方能看到对话发生过。

Solution

频道 transcript 成为群上下文的唯一事实源。Agent.Messages 只保留该 agent 自己的轮次，群上下文每轮从 transcript 按预算裁剪后拼进 prompt。这与知识库那边「history 只放对话、context 每轮现算」是同一个形状。

Wins

  • · locality：群上下文只从 transcript 算，一处可测
  • · 同一句发言从 3 份持久副本降到 1 份 + N 份纯引用
  • · agent 之间真的能互相看到 → 协作才成立
  • · 和知识库的 history 预算机制复用同一形状

注意

这条会把群聊从「广播」变成「多轮讨论」，语义升级。原来「频道是广播触发，非讨论收敛」是写进 docs/design.md 的已知限制。要真做的话得先确认：这是你想要的方向，还是继续维持广播语义、只修 #1 的那个恒 false bug。

3 · 投递失败了，但消息显示成功

main.go:315 SendToChannel errs 合并 · useSidecar.ts .catch → null

Strong in-process

Before · 消息先落地，投递结果丢失

  U->>S: 发消息

After · 投递是消息的一部分

用户 · 定个接口方案
后端 ✓ 前端 ✓ 测试 ✕ 队列满

点 ✕ 可重投

Message.Deliveries []Delivery —— 和 #1 的 Dispatch 返回值是同一个结构。

Problem

消息先落库先推送，之后才尝试投递。失败只拼成一个字符串返回，前端 .catch → return null 全吞。用户看到「消息发出去了」，实际有成员根本没收到，且无法发现或重试。

Solution

把投递结果变成 Message 上的数据（每个成员的成败），而不是一个抛出去的错误。UI 直接据此显示「谁收到了、谁没收到、为什么」。

Wins

  • · 部分失败变成可见状态，不再被 .catch 吞掉
  • · 重投成为可能（数据在，不在异常里）
  • · leverage：复用 #1 的 Delivery，零新增类型
  • · 「为什么没人理我」有了第二种可解释的答案

Problem

两个 Manager 逐字段同构，落盘、串行化、原子写各写一遍。真正的本质差异只有两处：投递是否异步有执行体、是否持有 agent 存活性。剩下的重复让每个新特性都要改两遍。

Solution

抽出有序集合 + 原子落盘这一层（泛型），两个 manager 各自只在上面加自己的本质职责。channel 侧顺带补上缺失的 Delete（前端已有删除按钮，后端无对应方法）。

Wins

  • · 落盘实现从 2 份降到 1 份
  • · 新特性只改一处，不再「两遍」
  • · leverage：Collection[T] 同时服务 channel / agent
  • · 补上 Delete，前端按钮不再指向空

为什么是 Worth exploring 不是 Strong：这是纯结构收益，不改任何可观察行为。而且泛型抽象一旦过度，会变成新的浅 module —— 它得先被 #1/#2 的真实需求压出来，不能凭空抽。建议排在 #1 之后。

5 · 单聊和群聊是两个输入框、三份 @解析、切换即丢草稿

ChannelView.tsx:74 · AgentView.tsx · main.go:378 · 切换 remount

Worth exploring in-process

Before · 三个地方各解析一遍 @

前端 · 补全

filtered = name.includes(q) || id.includes(q)

前端 · 插入

'@' + name + ' '

后端 · 解析

strings.Fields → 名字带空格即断

同一件事，三种语义，零共享

切换代价

· 未提交草稿丢失（remount）

· 滚动位置重置

· errors / tokenUsage 不清，跨会话串味

· 已删除 agent 的气泡永久失色（memberById 失配）

两个输入框 = 两套 textarea + mention 逻辑，
只有一件事不同：群聊能 @，单聊不能。

Problem

「发消息」这件事在两个视图里各写一遍，@语义在前端两处后端一处各写一遍且互不一致。切换会话时草稿和滚动丢失，跨会话的临时状态不清。

Solution

抽一个 composer module，把「草稿 + 补全 + 校验 + 提交」收进去，群聊只多开一个「可提及」能力。提及解析和 #1 的 Dispatch 共用同一份，不再有第二套语义。

Wins

  • · @ 语义从 3 份降到 1 份（与 #1 共用）
  • · 草稿跨切换保留
  • · 新视图零成本复用输入能力
  • · locality：输入相关 bug 集中在一个 module

实际后果

· 已删成员的历史气泡永久失色（memberById 查不到）

· 名字变成裸 ID 或空白

· 竞态窗口内可能对已删 agent 发事件

历史消息本身是对的 —— 删人不该删历史。
问题在展示层假设了成员一定存在。

Wins

  • · 历史消息永久可读，不依赖当前成员表
  • · 删人后 UI 不再有幽灵
  • · locality：参与者生命周期集中一处

为什么是 Speculative：影响面小、能绕开（删人不频繁）。但它暴露了一个真问题：Message 里存的 FromName 是快照还是引用？现在是快照，所以只要展示层别去查成员表就没问题 —— 这条要先定，再决定要不要做。

Top recommendation

先修 #1 的恒 false，再决定 #2 要不要改语义

两件事的紧急度完全不同。 #1 是 bug 不是设计：isRelevantToRole 的键和 a.Role 的值永远对不上，导致「不 @ 就没人回」。这在用户的真实体验里是「群聊是坏的」，但日志显示一切正常 —— 没有任何测试能发现，因为投递逻辑零覆盖。 把它抽成 deep module 的同时，这个 bug 自然会暴露成一个失败的用例。

#2 是产品决策不是重构：让 agent 看见彼此，会把「频道」从广播变成讨论。 docs/design.md 里写着「语义保持为广播，不做多轮收敛编排」—— 那是当时的决定。要不要改，得你说。 如果维持广播语义，#1 就够了；如果要真协作，先做 #2 再做 #1，因为 Dispatch 的接口形状取决于「群上下文从哪来」。
