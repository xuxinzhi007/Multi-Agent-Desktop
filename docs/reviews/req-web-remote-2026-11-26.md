# 需求卡 · Web 远程工作台（2026-11-26）

> 定位：**新需求，独立立项**，不并入当前的"体验修复"批次。
>
> **状态（2026-11-26 下午）：v1 已落地，方案被改成单页。**
> 原方案想额外做一版只读页（`/remote`），被用户否决——"不要做多套页面，直接使用桌面的"。
> 实际落地的是：网关 `POST /api/rpc` 反射到 `*API` + 前端 `mygo-http.ts` 装同签名 runtime，
> 浏览器跑的就是桌面这一套界面（`main.tsx` 三级判定）。旧的 `RemoteWorkbench` / `remote-api.ts` /
> `docs/remote-workbench.md` 已删除。

## 1. 一句话

把 Web 端从"浏览器预览替身"升级成"能看真状态、能点审批、能投递一句话的远程工作台"。

## 2. 为什么应该单独立项（而不是顺手改）

| 理由 | 说明 |
|---|---|
| **性质不同** | 当前三件（消息排序、插话、飞书一条卡）是修既有体验的错；这一件是**新增能力面**。混在一个批次里，验收标准和回滚边界会互相牵连。 |
| **验收标准不同** | 修复类的验收是"不再出错"；这一件的验收是"换一台设备也能推进任务"，需要跨设备的真实验证，不是单机跑一遍。 |
| **风险面不同** | 它会把本机执行权暴露到网络。必须单独过安全边界（token / 回环 / 写操作二次确认），不能夹在 bug 修复里悄悄上线。 |
| **依赖方向正确** | 它依赖消息排序先修好，否则 web 上看到的是同样错序的流——等于把乱的地基复制到第二个端。 |

## 3. 现状事实（已核实）

- 浏览器里没有 `globalThis.mygo`，`src/lib/preview-runtime.ts` 装替身：
  **数据是假的，写操作直接返回成功但不改状态**（`preview-runtime.ts` 文件头注释）。
- 后端 HTTP 面已存在：`internal/gateway/server.go` 的
  `/api/agents`、`/api/events`（SSE，复用桌面同一个 `Broker`）、`/api/approvals`、`POST /api/approvals/{id}`、`POST /api/inbound`、`/api/bindings`、`/api/status`。
- 鉴权已实现：配了 token 走 Bearer；没配 token 只允许回环地址。
- 缺的只有前端一层适配：把 `mygo` 的来源从"仅宿主注入"扩展到"宿主注入 或 HTTP/SSE 代理"。

## 4. 实际范围（已落地）

**不是"另做一版看板"，而是让同一套界面有第二个宿主。**

| 落地项 | 实现 |
|---|---|
| 通用方法入口 | `POST /api/rpc {method, args}` → `RPCInvoker` 反射到 `*API`（`internal/gateway/rpc.go`） |
| 前端宿主替身 | `src/lib/mygo-http.ts`：`call`→`/api/rpc`，`on/once`→`GET /api/events`（SSE） |
| 入口判定 | `main.tsx` 三级：宿主注入 → 网关可达 → 预览替身 |
| 只读/审批/投递 | 不需要单独端点：`ListAgents` / `ListApprovals` / `DecideApproval` / `PromptAgent` 都已在方法表里 |
| 第二套页面 | **删除**（`RemoteWorkbench`、`remote-api.ts`、`docs/remote-workbench.md`） |

## 5. 非目标（v1 明确不做）

- 不做多用户/多租户，不做公网暴露（默认只回环，跨设备走 Tailscale 之类）；
- 不做完整 RPC 桥（那是 v2）；
- 不做移动端原生壳；
- 不替换桌面端，web 是**补充入口**。

## 5.5 多端一致性（v1 上线当天就踩到，已补）

**问题**：桌面处理完的审批，网页仍显示；点下去报「审批已失效或已完成」。

**结论**：这是"第二个客户端"才暴露的一类问题——单端时"决定"和"收卡"在同一个页面里，
事件丢不丢都看不出。**只靠事件当唯一真相**就是根因。

**已补的三条对账（都不做定时轮询）**：

| 触发 | 动作 |
|---|---|
| `gateway.connected`（每次连上/重连都会发） | 全量覆盖 approvals + agents |
| 窗口重新获得焦点 / 切回可见 | 全量覆盖 |
| 决定失败且原因是「已失效/已完成」 | 按已收卡处理（幂等），原因照常抛给界面 |

**已补（本轮）**：SSE 加 `id:` 与 `Last-Event-ID` 续传 —— broker 保留最近 256 条
（`replayLimit`），`SubscribeSince` 先补发再进实时通道，连接帧回带 `replayed/since`。
这样断线窗口内的事件不再丢；超出窗口由三条对账兜住，两层互补。

## 6. v2（等 v1 验证过再做）

把 MyGo 注册的方法摊成一个通用 `POST /api/rpc {method, args}`，
`on()` 走 `GET /api/events` —— 桌面与 web **共用同一份方法表、同一条事件流**，
而不是逐个端点各写一遍（那样必然变成两套 API 漂移）。

## 7. 验收清单

- [ ] 浏览器打开后标题不再显示「预览 · Multi-Agent Desktop」，且能看到真实的 agent 列表；
- [ ] 桌面里发起的任务，web 上**秒级**看到同一条事件流（证明用的是同一个 Broker，不是轮询）；
- [ ] web 上点「允许一次」，桌面端与该审批相关的那一轮继续往下跑（证明是同一个审批单，不是两份状态）；
- [ ] 未配 token 时，非回环地址访问返回 401；
- [ ] 后端断开时，web 显示"未连上后端"，**而不是掉进假数据**（兜底必须是显式失败，不是静默 mock）。

## 8. 风险与红线

- **钓鱼式写操作**：web 端任何写操作都必须二次确认（审批除外，审批本身就是确认）；
- **走漏到局域网**：默认 `127.0.0.1` 绑定；开远程必须先配 token，不允许"空 token + 0.0.0.0"这种组合；
- **假数据误导**（已有问题，建议本批次顺手修）：预览模式下写操作"返回成功但不改状态"，
  会让界面显示"发出去了"而实际没发 —— 应改成显式提示「预览模式：未真正执行」，避免被当成 bug 报。

## 9. 成本与排期

| 项 | 预估 | 实际 |
|---|---|---|
| 通用 `/api/rpc` 桥 | 0.5d | 0.4d（`rpc.go` + 6 条测试） |
| 前端 `mygo-http.ts` | 0.4d | 0.3d |
| 三级判定 + 删 `/remote` | 0.2d | 0.2d |
| **合计** | ≈1.1d | **≈0.9d** |

**已验证**：浏览器打开 `localhost:5173` → 标题 `Multi-Agent Desktop · Web`、`dataset.web=1`、
14 个 agent 与桌面同名同模型、控制台 0 错误；`API.ListAllModels`（ctx 形参）与
`API.AgentMessages(id, 5)`（位置参数）在 `/api/rpc` 上都返回真实数据。

**踩到并修掉的缺陷**：反射里 `context.Context` 一开始按形参下标取实参，导致
`PromptAgent(ctx, req)` 收不到 `req`——`TestRPCInvokerSkipsContext` 抓到了，已改为独立的实参计数器。
