## 0. 一句话结论

真实产品在「多 agent 并发」这件事上，**没有一个把并发状态放在浮层里承载全文**。
它们的共同解法是三层分工：

```
第 1 层  常驻极简指示器   → 只回答「有几个在跑 / 有几个等我」        （菜单栏、footer、tab badge）
第 2 层  可展开的列表     → 每个 agent 一行：名字 + 一句话状态 + 年龄 （agent view 表格、pill bar）
第 3 层  完整会话        → 进入后才是 transcript                    （attach / 打开 tab）
```

✅ 三层分工在 **Claude Code agent view**、**Warp 通知体系 + 编排 pill bar**、**Devin agent sidebar** 三处独立出现，是三家的共识而非一家之言。

而「agent 之间的交互关系」表达方式，三家给出的答案是**同一个结构：parent/child 的扁平行，而不是图**。理由在 §2.4 给出（Warp 明确写了「orchestrations 今天恰好只有一层」）。

## 1. 主流产品如何呈现「多个 agent 并发工作」

### 1.1 Claude Code —— `agent view`：全屏表格 + peek 面板 + footer 计数

这是目前对「并发状态密度」给出最明确规格的产品，几乎可以直接照抄信息架构。

**① 主形态是一张全屏表格，不是卡片网格。** ✅
- `Claude Code · agent-view`：*"Run `claude agents` to open agent view. It takes over the full terminal and lists every session grouped by state, with pinned sessions and the ones that need you at the top. Each row shows the session's name, current activity, and its age, counted from when the session was created; a finished session's age freezes at how long the run took."*
- → **一行 = 一个 agent。字段恰好三个：name / 一句话 activity / age。** 没有 token 数、没有模型名、没有进度条。这是「扫读密度」的上限样本。

**② 状态用「图标颜色 + 图标形状」两个正交维度编码。** ✅
颜色表（原文照抄）：

| 状态 | 图标 | 含义 |
|---|---|---|
| Working | 动画 | Claude 正在跑工具或生成回复 |
| Needs input | 黄色 | 在等**只有人**能提供的东西：问题的答案、权限决定、sandbox 提示、MCP 输入请求 |
| Idle | 变暗 | 无事可做，等下一个 prompt |
| Completed | 绿色 | 成功完成 |
| Failed | 红色 | 出错结束 |
| Stopped | 灰色 | 被 `Ctrl+X` / `claude stop` / 外部杀死 / 后台服务关闭时结束 |

形状表（原文照抄，**与颜色独立**）：

| 形状 | 含义 |
|---|---|
| `✻` / 动画 `✽` | 进程在跑，或会话等人输入 |
| `∙` | 进程已退出（仍可 peek；回复或 attach 时从存档对话重启） |
| `✢` | `/loop` 会话在两次迭代间睡眠，行上显示轮次和倒计时 |

- 来源：`Claude Code · agent-view`，「Read session state」小节。
- ✅ **这一点非常关键**：颜色表达「要不要我管」，形状表达「进程还活着吗」。两个问题分开编码。**我们的 `mini.tsx` 目前只用颜色 + pulse 动画，把「活着」和「等我」压在同一维度**（见 §4.1）。

**③ 分组顺序是「按需我介入的紧急度」，不是按创建时间。** ✅
- *"Agent view groups sessions so the ones that need input are at the top, with **Ready for review** and **Needs input** above **Working** and **Completed**."*
- 且分组名和状态名**不一一对应**（原文明确说明）：`Ready for review` 来自「有 open PR 且待 review 或 checks 失败」，`Completed` 把 finished/failed/stopped 三类合在一起。
- 🔶 → **推论：状态枚举（给机器）和分组标签（给人）应当是两个东西。** 我们的 `Status`（idle/running/queued/error）适合做枚举，但浮层上展示的分组标题不该叫「出错」，而该叫「需要你处理」。

**④ 一行里的那一句状态，是模型生成的摘要，不是日志尾巴。** ✅
- *"The one-line summary in each row is generated by a Haiku-class model so the row can tell you what the session is doing, what it needs, or what it produced without opening the transcript. While a session is actively working, the row text updates at most once every 15 seconds from the session's own recent output without sending a model request, and the model writes a fresh summary when each turn ends."*
- *"A working row shows what the session says it's doing, and **a blocked row shows the question it's asking**."*
- ✅ **代价是明确写清的**：每次摘要都是一次真实模型请求，按该会话同样的数据条款计费；可用 `ANTHROPIC_DEFAULT_HAIKU_MODEL` 指定小模型。
- 🔶 这是本报告里**信息密度最高的一条设计**：**浮层上那一行字的价值 = 「它现在到底在干嘛或者要问我什么」，而这个必须由模型总结，日志原文没用。** 我们的 `mini.tsx:45-57` 现在抓的是 `agentDelta` 的**最后 100 字符原文**（`lastOutputs.current[a.id].slice(-100)`），这个截断在 token 流中间，几乎必然是可读性最差的片段。

**⑤ peek 面板：比行多一点，比完整会话少得多。** ✅
- *"Press `Space` on a selected row to open the peek panel. It opens with the sentence the row truncates at the terminal edge"* —— 三种状态给三种内容：
  - 等我的会话 → **它正在问的那个问题原文**，放在回复输入框上方
  - 已完成的会话 → **它的结果**
  - 工作中的会话 → **完整的状态句子**
- 额外一行只在「等我 / safe mode」时出现：`waiting 3m`（等了多久）—— ✅ **与行右边缘的 age（从启动算起）是两个不同的数字。**
- peek 面板里可以直接回消息：`Enter` 发送。特殊处理：
  - 会话在忙 → 除 `/model` `/effort` `/rename` `/usage` 外，**回复进入消息队列而不打断**
  - 回复正好是 `/stop` → **立刻停止会话**（不投递）
  - 会话在等权限提示/对话框 → **回复不会解开它**，只能 `→` attach 后回答；消息在队列里等
- 🔶 → **「轻量层能不能回话」这个决策上，Claude Code 的答案是「能，但只能回文本；结构性交互（权限弹窗）必须上升一层」。** 这给了浮层一个清晰的能力边界。

**⑥ 常驻的极简指示器在 footer，不是独立悬浮窗。** ✅
- *"In a regular `claude` session, pressing `←` on an empty prompt opens agent view, and a `←` hint in the footer reports on your background sessions"*
- *"**Waiting count**: while background sessions wait on your input, the same spot counts them, such as `← 2 agents`, or `← 99+ agents` when more than 99 wait. The count refreshes about **every ten seconds** while the terminal is focused and **immediately when focus returns**"*
- *"**Finished count**: when background sessions finish successfully while none wait on your input, the footer briefly shows how many finished, such as `← 2 done`"*
- *"The waiting count briefly **changes color** when it goes up or down and when a background session finishes successfully. If you turn on `prefersReducedMotion`, you see neither the color change nor the done count."*
- 终端 tab 标题也随之变：`2 awaiting input · claude agents`
- ✅ **三个可直接照抄的细节**：
  1. **99+ 的上限折叠**（我们的 `mini.tsx:170` 是 `.slice(0, 8)`，但**没有任何「还有 N 个」的提示**——8 个以外的 agent 在浮层上彻底消失）。
  2. **计数在失焦时节流到 10 秒一次，重新聚焦立刻刷新** —— 这是省电的直接手段。
  3. **`prefersReducedMotion` 时连颜色变化都关掉，并且明确说明「你看不到 done 计数」** —— 不是简单地把动画时长设成 0。

### 1.2 Warp —— 三档通知强度：toast / mailbox / tab badge

Warp 的并发表达是「**按打扰成本分三档**」，且明确区分 in-app 与系统级。

✅ **① Toast（浮动 tóast，在窗口角落）** —— `Warp · agents/capabilities/agent-notifications`：
- *"Floating toast notifications appear in the corner of the Warp window when an agent in another tab needs attention. Toasts **auto-dismiss after a few seconds**. Hover over a toast to **pause the timer**, or click it to jump directly to the agent's session."*
- *"**Up to two toasts are visible at a time.** If additional notifications arrive, the oldest toast is replaced."*
- → 截图描述（官方图注）：*"A Warp toast notification in the **upper-right corner** showing an agent task completed, with an **Open conversation** action and a **keyboard shortcut chip**"*
- 🔶 → **「最多 2 个、满了替换最老的」是防止 toast 风暴的硬规则**。我们的 `Toast.tsx` 需要同样的上限，否则 N 个 agent 同时结束会糊屏。

✅ **② Notification mailbox（铃铛 + 侧栏收件箱）** —— 同上文档：
- *"The notification mailbox is a **sidebar panel** that collects all agent notifications in one place. Open it from the **bell icon in the top-right corner**."*
- 含 **Filter tabs**：`All tabs` / `Unread` / `Errors`；*"If there are no unreads or errors, those filters **don't appear**"*
- `Mark all as read`；点击任一条直接跳该 agent 的 tab
- 键盘：`↑`/`↓` 选择、`Enter` 打开、`Shift+Tab` 循环 filter tab、`Esc` 关闭
- → **「通知会累积成可回溯的列表」而不是闪过就没了**。

✅ **③ Tab status indicators** —— 同上文档：
- *"Each **tab displays an icon** reflecting its agent's current state — **working, blocked, completed, or errored**. Tabs with unread notifications show an **attention badge** so you can spot which sessions need action, even with many tabs open."*
- *"Notifications are **automatically marked as read when you navigate to the agent's tab**."*
- ✅ **「已读」的定义是「你打开过那个 tab」，不是「你点了通知」** —— 天然幂等，不需要额外的已读按钮状态机。

✅ **④ 状态枚举只有四个，且有序**：`working / blocked / completed / errored`。注意 **`blocked` 是独立状态**，不是 `error` 的子类，也不是 `running` 的子类。这与 Claude Code 的 `Needs input` 完全同构。
- 云端另有一套 6 态 run 状态（见 §2.2）。

✅ **⑤ 通知类型只有三种**：*"Warp categorizes agent notifications by what happened: **Complete** … **Request** — the agent is blocked and needs your input. This includes command approval, permission requests, and idle prompts where the agent is waiting for you. **Error** …"*
- 🔶 → **`Request` 把「等我批准」和「等我聊天」合成一类，因为对人而言后果一样：不动我就不走了。** 我们的 `mini.tsx` 目前没有这个状态（只有 running/queued/error/idle），所以「agent 在等人批准」会被显示成 `running` + pulse 动画——**用户无法区分「它在忙」和「它在等我」**。这是当前浮层最大的语义缺口。

### 1.3 Cursor —— Agents Window（与 IDE 并存的第二形态）

✅ `Cursor · agent/agents-window`：
- *"The Agents Window is Cursor's **agent-first interface**. It provides a unified workspace to build with agents across repos and environments, including local, cloud, remote SSH, and more. It combines the power of **parallel agents** with the depth and control of a development environment."*
- *"You can **switch back to the editor anytime, or have both open simultaneously**."*
- 入口：`Cmd+Shift+P` → `Open Agents Window`；回 IDE：`Cmd+Shift+P` → `Open IDE`；*"If you want to view or edit files without leaving the Agents Window, you can type `Cmd+P` to search files, or `Cmd+Shift+F` to search all files."*
- ✅ **这是本报告里最重要的「两种展示密度」证据**：Cursor 不是「主窗 + 小浮窗」，而是**同一份 agent 数据流，两个对等的一等窗口**，随时可切、可并存、且**目标窗口内保留了对方的核心动作**（`Cmd+P` 文件搜索在 Agents Window 里仍可用）。

✅ `Cursor · subagents`：*"**The subagent task card shows which model ran.**"* —— 子 agent 在 transcript 里以**卡片**形式内联出现，不是另开一行。
✅ `Cursor · agent/projects`：*"A Project maintains context over months of work, **delegates tasks to many agents in parallel**… **The coordinator plans and delegates.** It creates and manages agents on your behalf, running as many in parallel as the work needs. Because it **delegates rather than executes**, it stays responsive to your direction."*
✅ 另有 `Agents` 列表：「*The chat then appears **under the Project row** and in the **`Agents` list above the Project's chat input**」—— 即 **Project 行下方缩进挂 agents**，与 ADR-0001 P3「子 agent 侧栏嵌套在父 agent 下方」的判断一致。
✅ 进度语音（`cursor.com/changelog` 2026-11-06）：*"It shares **short progress notes** while it works and a **brief answer when it's done**, so you usually hear a short update instead of the full written reply."*
- 🔶 → 「短进度注记 + 完成时短答」这个信息颗粒度，与 Claude Code 的行摘要同源。**两家独立收敛到「一句话」，这是强信号。**

### 1.4 Devin Desktop —— Agent Command Center + 原生通知

✅ `Devin · desktop/agent-command-center`：
- *"The Agent Command Center is a new surface inside Devin Desktop 2.0 for managing **every agent you have running, both local and cloud, in one place**. **Local agents** — Agent sessions running in your editor. **Cloud agents** — Devin sessions running on their own VMs."*
- *"You can switch to the Agent Command Center **directly from Devin Desktop without leaving the editor**."*
- **Agent sidebar**：*"The sidebar lists every session in the workspace and can be shaped to fit how you work: **Filter, sort, and group** sessions per workspace. **Right-click a session to rename, organize into folders, or start child sessions.**"*
- **锁定的会话**：*"Sessions are **locked while their agent is running**: they appear **greyed out and are read-only** until the agent finishes. If you are signed out, session tabs show a sign-in prompt rather than an error."*
- ✅ **通知策略（对「要不要做系统通知」这个问题是直接答案）**：*"Devin Desktop can send a **single native OS notification** when an agent session finishes or needs your input **while Devin Desktop is in the background**. **One setting covers every agent** — Devin Local and ACP agents alike — so you get **one notification per session rather than one per surface**. Notifications are **off by default**."*
- ✅ **明确声明不自立门户**：*"The Agent Command Center **does not replace the editor**. It is integrated with the existing Devin Desktop editor features so you can always jump back into a session and make last-mile edits manually."*
- 🔶 → 「渲染为 greyed out + read-only」是一个很省的表达：**不需要进度条，用「能不能编辑」这个既有交互状态顺带表达「还在跑」**。

✅ `Devin · cli/subagents`（子 agent 的可见性给了最具体的字段清单）：
- *"When background subagents are running, an **indicator appears below the input area** showing their status. You can navigate to the indicator by pressing `↓` from the input area, then press `Enter` to **open the subagent panel**."*
- *"When a foreground subagent is running, the spinner displays **"Subagent running · Ctrl+B to run in background"**."*
- *"**Subagent Panel**: … It shows each subagent's **profile, title, status, elapsed time, and tool call count**."*
- *"Subagent activity **survives a session reload**, so the panel still reflects your subagents after resuming."*
- ✅ **五个字段**：profile / title / status / elapsed / tool call count。🔶 注意它**比 Claude Code 多一个 `tool call count`** —— 这是「它还在动」的廉价证据，不需要模型摘要。

### 1.5 Raycast —— HUD 与「同一内容的两种密度」的教科书样本

✅ `Raycast · api-reference/feedback/hud`：
- *"When the user takes an action that has the side effect of closing Raycast (for example when copying something in the Clipboard), you can use a HUD to confirm that the action worked properly."*
- *"**A HUD will automatically hide the main window and show a compact message at the bottom of the screen.**"*
- 签名：`showHUD(title: string, options?: { clearRootSearch?, popToRootType? })` —— ✅ **HUD 只能带一个 title 字符串，没有图标字段、没有进度字段、没有按钮字段。**
- 🔶 → **这是「轻量层承载多少信息」的最硬的边界证据：一个字符串。** 我们的 `mini.tsx` 承载了 8 个状态点 + 悬停 tooltip + 展开列表 + 右键菜单 + 点击数，信息量已经**超过 Raycast 主窗的入口**，但展示面积只有 380×52。

✅ `Raycast · manual/notes`（**同一内容两种密度的最佳实例**）：
- *"Our note-taking experience comes with three commands: **Raycast Notes**: This command **toggles the Notes window**…"*
- *"**Show Notes Toggle Button in Menu Bar**: Add a button to the menu bar that shows or hides the Notes window."* → ✅ **菜单栏按钮 = 开/关同一个窗口，不是「另一个迷你窗口」。**
- *"**Escape Key Loses Focus**: Pressing Esc in Notes moves focus away from the window **instead of closing it**."* → ✅ **明确区分「失焦」与「关闭」。**
- changelog 确认另有一条**独立于窗口的浮层**：*"**Notes**: The **pinned Notes window stays visible when switching Spaces**"* 与 *"you can now **hide your Notes window while screen sharing** again"*（`raycast.com/changelog`）。
- 🔶 → **Raycast 的做法是「一个窗口 + 三种附着策略」（普通 / pinned 跨 Space / 录屏时隐藏），而不是做两个界面。** 这与我们要回答的「避免做成两个独立应用」直接对应。

✅ `Raycast · manual/ai/agents`：Raycast 的 "Agent" 是**预设（role + model + tools）**，不是并发实例。*"Instead of configuring from scratch each time, you save the role, model, and tools as an Agent and pick it when you need it."*（v1 里叫 Presets。）
- 🔶 → **提醒：「Agent」这个词在我们的产品里指并发实例，在 Raycast 里指角色预设。写文档时不要混用。**

### 1.6 Linear —— agent 作为「一等公民用户」

✅ `Linear · docs/agents-in-linear`：
- *"Agents are designed to work seamlessly **alongside human teammates**… **Delegate issues by assigning the issue to the agent.** … **@mention them in comments or descriptions**…"*
- *"**Agent user pages show issue activity and contributions.**"*
- *"In the **My issues** view, issues that you've delegated to agents **will still appear** — so you maintain visibility and control over the work in progress."*
- *"Custom views filtered by **`Delegate`** to monitor agent involvement… Use **Insights sliced or segmented by `Delegate`** to measure how much work is being directed to and handled by agents."*
- *"Agents **cannot sign in to the app, access admin functionality or manage users**."* 且 *"Are agents billable seats? **Agents are not counted as billable seats**."*

🔶 → **Linear 完全没有为 agent 做新 UI。** 它把 agent 塞进既有的 `assignee` / `@mention` / `Activity` 三件套里。这是「避免做成两个独立应用」的另一种极端解法：**不给 agent 特殊外观，复用人的交互原语。**
对我们的含义：频道里 agent 发的消息**不需要 agent 专属气泡**；`@` 与「指派人」这两个原语已经足够表达「谁派了谁」。

## 2. 如何表达「agent 之间的交互 / 协作关系」

> 这是本报告最值得直接采用的部分。三家产品给出的结构**高度一致**，且都**明确回避了「图画式的关系图」**。

### 2.1 Warp：orchestration pill bar（横向 pill 条）—— 关系表达的最完整规格

✅ `Warp · platform/orchestration` 与 `Warp · platform/managing-cloud-agents`：

- *"in the Warp app, while you're viewing the parent agent, a **horizontal pill bar above the agent view header shows the parent on the left and one pill per child. Each pill displays the child's name and a status badge that updates live.** Click a pill to **switch the pane to that child's conversation in place**; click the parent pill — **or the breadcrumb that replaces the pill bar while you're viewing a child** — to return."*
- ✅ **父/子关系的表达只需要两样东西**：
  1. **位置**：父在最左，子依次向右（不是树、不是缩进）。
  2. **原地切换 + 面包屑**：进入子以后 pill bar 变成面包屑，退回父。
- 🔶 → **「原地换 pane + 面包屑」比「新开一层窗口」便宜得多**，而且天然回答了「我现在的视角相对谁」。我们 ADR-0001 P3 定了「侧栏嵌套在父 agent 下方」——那是**列表视图**的答案；**浮层/顶部区域**应当用 Warp 的 pill bar。两者不冲突，因为它们服务的密度不同。

### 2.2 Warp：6 态 run 状态机（「谁在等谁」有了可判定的枚举）

✅ `Warp · platform/orchestration`，child run 的用户可见状态，**原文照抄**：

| 状态 | 含义 |
|---|---|
| `INPROGRESS` | 正在执行（或因 blocked 后重启而恢复执行） |
| `SUCCEEDED` | 成功完成 |
| `FAILED` | 终态失败 |
| `BLOCKED` | **在等用户动作**（例如命令批准、权限请求） |
| `ERROR` | 启动或执行期间出错 |
| `CANCELLED` | 达到终态前被取消 |

✅ **父子如何互相感知（这是「交互关系」的机制层，不是 UI 层）**：
- *"**The parent's transcript** — the parent agent receives child state transitions as it runs and **reflects them in its own conversation**."*
- *"**Blocked children** — if a child blocks on user input (for example a command approval request), **open that child from the pill bar to resolve the block. The parent's transcript also reflects the child's `BLOCKED` state so the parent can wait, send a follow-up, or cancel the child.**"*
- 🔶 → **「子 agent 卡住」这件事同时出现在两个地方：子的 pill + 父的 transcript。** 这不是冗余，因为两者回答不同问题（子 pill = 需要我去点；父 transcript = 父为什么停下来了）。

✅ **消息总线（真正跑在底下的东西）**：
- *"Orchestration is built on a **durable, server-backed message bus**. Every agent in an orchestration — parent and children — has **its own inbox addressed by its agent ID**, and the parent and children send each other **short, structured messages**…"*
- *"Each run emits **lifecycle events** on the same infrastructure when its state changes — the six states listed above. **The parent observes these events to decide what to do next (keep waiting, send a follow-up, spawn a replacement, finish) without polling any child.**"*
- *"Use messages for coordination signals — **handoffs, decisions, blocked-on-input requests, status updates, and final results** — rather than for piping full transcripts around. **The parent's prompt to a child and the child's final output carry the substance of the work; messages are how the agents talk *about* the work as it happens.**"*
- ✅ **权威性**：*"The parent's own status reflects only its own work — **a parent can finish successfully while a child is still running or has failed**. To verify that an orchestration completed, check each child individually…"*
- 🔶 → **两条必须抄进我们设计的规则**：
  1. **父状态 ≠ 子状态聚合**。父 `SUCCEEDED` 时子可能仍 `BLOCKED`。任何「总体进度」聚合都必须显式声明不含什么。
  2. **消息只传协调信号，不传 transcript。** 这直接对应我们 `collaboration-plan.md` 里「共享 transcript vs 广播」的争论——Warp 的答案是：**两者都有，但用途分离**。

✅ **深度限制（为什么不做图）**：
- *"**Orchestrations today are exactly one level deep: a parent and its direct children.** The Warp app, the Oz web app, and the Warp Platform API **render that single level**."*
- 对照 `Claude Code · agent-teams`：*"Subagents report results back to the main agent. In agent teams, **teammates share a task list, claim work, and communicate directly with each other.**"* 且 *(Claude Code)* 团队是**平级**的 lead + teammates，**不是树**。
- ✅ **两家都收敛到「最多一层」，且都是平的。** 🔶 → **这解释了为什么不需要关系图**：当深度恒为 1 时，pill 条 / 缩进列表就够了，图的成本（布局算法、缩放、点击命中）全是白付。

### 2.3 Claude Code：agent teams 的「谁在等谁」

✅ `Claude Code · agent-teams`：
- **协作 vs 委托的差别被明确写出来**：
  - Subagents：*"Own context window; **results return to the caller**"* / *"Return a result to the caller."* / *"Main agent manages all work."*
  - Agent teams：*"Own context window; **fully independent**"* / *"**Teammates message each other directly**"* / *"**Self-coordination through messages, plus a shared task list** for agents that have the Task tools."*
- **共享任务列表 + 依赖**：*"Tasks have three states: **pending, in progress, and completed**. A task can also **depend on other tasks and shows as `blocked` in the task list until they're completed**. Teammates **don't self-claim a blocked task**, but you or the lead can still assign it."*
- **两种指派**：lead 显式指派 / teammate 完工后**自领**下一个（`Self-claim`），且 *"Task claiming uses **file locking** to prevent race conditions."*
- **plan approval 是一种显式的关系**：*"When that teammate finishes planning, it **sends a plan approval request to the lead**."*
- **shutdown 有握手**：*"The lead sends a shutdown request. The teammate can **approve, exiting gracefully, or reject with an explanation**."*
- **面板折叠规则（给 UI 的直接指令）**：*"An **idle** teammate's row **stays in the panel while any teammate or subagent is still working**… Once **every** agent in the panel is idle, idle rows **hide after 30 seconds** and reappear on the teammate's next turn; the teammate stays running and addressable while hidden."* / *"When more than three teammates are idle at once, the rows beyond the first three **collapse into a single row that counts** the collapsed teammates, such as `2 idle agents` when five are idle."*
- 🔶 → **「空转的 agent 主动让位」是并发 UI 的一条硬规则。** 我们的 `mini.tsx` 把 idle 的 agent 也画成状态点（只是 `opacity: 0.35`），**占据了和 running 一样的位置**。当 8 个 agent 里 7 个 idle 时，浮层看起来仍然很挤，而实际上只有 1 个值得看。

✅ **消息投递的可见性**：`Claude Code · cross-session-messaging`：
- *"If Claude is busy and hasn't received the message yet, **scroll to the end of the transcript, where the message is listed under `Waiting to be delivered`**."*
- *"The watched session shows a line saying **another process asked to be told when the session is next idle**. The asking session shows the notice as a line **naming the watched session**."*
- `/list-agents` 的输出**分行分类**：*"**Subagents**: agents running inside the current session. **Your other local sessions**… **Your Remote Control sessions on other machines**… labeled `Remote Control`. Claude Code shows **`offline`** as the status of a session whose connection has dropped."*
- 🔶 → **「消息排队中」必须是可见状态。** 我们现在 `main.go:315` 的投递失败会被 `.catch→null` 吞掉（见 `collaboration-plan.md` 已记录的「消息显示成功但没人收到」），而 Claude Code 给排队设了专门的一行 UI。**表达关系的前提是「消息没到」这件事看得见。**

### 2.4 汇总：三家的关系表达对照

| 产品 | 父子关系怎么画 | 谁在等谁怎么表达 | 深度 | 来源 |
|---|---|---|---|---|
| **Warp** | 横向 pill 条：父在左、子向右；进入子后变面包屑 | 子 pill 上的 live status badge，`BLOCKED` 是**独立状态**；父 transcript 里也反映子的 `BLOCKED` | ✅ 恰好一层 | `Warp · platform/orchestration` |
| **Claude Code**（teams） | agent panel 里平铺，lead + teammates，**无层级缩进** | `Needs input`（黄）+ 黄行直接显示**它正在问的问题原文**；`/list-agents` 里标 `offline` | 平级 | `Claude Code · agent-teams` / `agent-view` |
| **Claude Code**（subagents） | *"a panel **below the prompt input**, with one row for the main session and one for each fork"* | 行图标（颜色+形状）+ 行摘要 | 可嵌套（有 depth 限制） | `Claude Code · sub-agents` |
| **Cursor** | Project 行下方挂 agents；子 agent 以 **task card** 内联在 transcript 里 | card 上显示跑了哪个 model | — | `Cursor · agent/projects` / `subagents` |
| **Devin** | 右键 session → **Start child sessions**；侧栏可 folder 分组 | session 列出 profile/title/status/elapsed/tool count；运行中**greyed out + read-only** | 可嵌套（`max-nesting`） | `Devin · desktop/agent-command-center` / `cli/subagents` |
| **Linear** | 不表达——复用 `assignee` / `@mention` | `Delegate` 字段可筛选 | — | `Linear · docs/agents-in-linear` |

✅ **共性结论（三个独立产品一致，可信度高）**：
1. **关系靠「邻近 + 一致性切换」，不靠连线。** 位置（左→右 / 上→下缩进）、面包屑、点击原地换 pane。
2. **`blocked` / `needs input` 必须是独立状态**，且**必须能一眼看到「它在问什么」**，而不只是「它卡住了」。
3. **父状态不聚合子状态**，需要分别检查。

## 3. 「同一内容的两种展示密度」的成熟模式

> 这一节直接回答「如何避免做成两个独立应用」。

### 3.1 模式 A：**一个窗口 + 可变附着力**（Raycast Notes）

✅ `Raycast · manual/notes` + `raycast.com/changelog`：
- 菜单栏按钮 = **toggle 同一个 Notes 窗口**（不是开一个迷你版）
- `pinned Notes window stays visible when switching Spaces` → **附着策略**（跨 Space）
- `hide your Notes window while screen sharing` → **另一个附着策略**（录屏隐身）
- `Escape Key Loses Focus` vs 关闭：**失焦与关闭是两个不同的用户意图**

🔶 → **同一个组件树，切换的是「窗口属性」而不是「渲染哪套 UI」。** 对我们最直接的映射：`mini.html` 和 `index.html` 应当是**同一套状态源、同一套组件**，差异只在（a）渲染哪些节点、（b）窗口属性。**现在的 `src/mini.tsx` 是 423 行的独立实现，与 `App.tsx` 零共享** —— 这正是「做成两个独立应用」的征兆。

### 3.2 模式 B：**两个对等窗口，各自保留对方的核心动作**（Cursor Agents Window）

✅ `Cursor · agent/agents-window`：
- *"You can switch back to the editor anytime, **or have both open simultaneously**."*
- *"If you want to view or edit files without leaving the Agents Window, you can type `Cmd+P` to search files, or `Cmd+Shift+F` to search all files."*
- 🔶 → **判据：两个形态不互为「精简版」，各自都要能完成该形态下的完整任务闭环。** Agents Window 不是「编辑器的预览窗」，它能搜文件、能编辑；编辑器也不是「Agents Window 的回退」。

### 3.3 模式 C：**跨产品统一为一个通知面**（Devin）

✅ `Devin · desktop/agent-command-center`：
- *"**One setting covers every agent** — Devin Local and **ACP agents** alike — so you get **one notification per session rather than one per surface**."*
- 🔶 → **「每个 session 一条通知，而不是每个界面一条」** 是避免「两个应用」体感的关键：如果主窗和浮层各自弹一次，用户立刻感知到是两个东西。

### 3.4 模式 D：**原地替换内容而非打开新容器**（Warp pill bar / Claude Code peek）

✅ Warp：*"Click a pill to **switch the pane to that child's conversation in place**"*
✅ Claude Code：`Space` 打开 peek 面板（**浮在当前视图上的一层，不切走**）；`→` 才 attach 成完整会话。
✅ Claude Code `/btw`（`interactive-mode`）：*"In the terminal, they appear in a **dismissible overlay**. … The question and answer **never enter the conversation history**."* 且 *"**Available while Claude is working**"*，`f` 键可把这条侧问题 **fork 成 background subagent**。
- 🔶 → `/btw` 是本报告里最精巧的一例：**轻量层不只读，还能「升级」** —— 一条在浮层里问的问题，按 `f` 就地变成一个有完整工具权限的后台 agent，且**原会话不受影响**。这是「两种密度」之间的**单向升级通道**，而不是两个平行宇宙。

### 3.5 模式 E：平台规范（Apple HIG）

🌐 `Apple HIG · the-menu-bar`（`.md` 原文）：
- *"A **menu bar extra** exposes app-specific functionality using an icon that appears in the menu bar when your app is running, **even when it's not the frontmost app**."*
- **Display a menu — not a popover — when people click your menu bar extra.** *"Unless the app functionality you want to expose is too complex for a menu, **avoid presenting it in a popover**."*
- *"When necessary, the system **hides menu bar extras** to make room for app menus. Similarly, if there are too many menu bar extras, the system may hide some to avoid crowding app menus."* → ✅ **常驻指示器随时可能被系统隐藏**，不能作为唯一入口。
- *"The menu bar's height is **24 pt**."* / *"**Consider using a symbol** to represent your menu bar extra."*

🌐 `Apple HIG · popovers`：
- *"**Use a popover to expose a small amount of information or functionality.** Because a popover **disappears after people interact with it**, limit the amount of functionality in the popover to **a few related tasks**."*
- *"**Consider using popovers when you want more room for content.** Views like **sidebars and panels take up a lot of space**. If you need content only temporarily, displaying it in a popover can help streamline your interface."*
- *"Position popovers appropriately. Make sure a popover's **arrow points as directly as possible to the element that revealed it**."*
- 🔶 → **浮层的信息量上限是「几件相关的事」，且交互完就消失。** 我们 `mini.tsx` 的展开态（`expanded`，高度从 52 涨到最多 372）承载了完整列表 + 状态 + 时长 + 输出片段 + 右键停止 agent —— 这已经不是 popover，是 **panel**，而 HIG 明确说 panel「take up a lot of space」。

### 3.6 对照：我们现在的形态 vs 成熟模式

| 维度 | 现状（`src/mini.tsx` / `App.tsx`） | 成熟做法 | 差距 |

## 4. 对我们产品的具体含义（🔶 全部为推论，需设计评审）

### 4.1 补齐「等我」这个状态 —— 这是当前最大的语义缺口

✅ 事实：Warp 有 `blocked` / `Request`；Claude Code 有 `Needs input`（黄，且**行上直接显示它在问的问题**）；Devin 有 *"needs your input while Devin Desktop is in the background"* 触发通知。
✅ 事实（本仓库）：`internal/agent/manager.go:16-24` 定义 `type Status string`，取值 **`idle` / `running` / `queued` / `done` / `error`** 五个（`StatusIdle/StatusRunning/StatusQueued/StatusDone/StatusError`）。`agent.status` 事件在 `manager.go:456,472,520`（进入 queued/idle/running）与 `finish()` 路径发射。
✅ 事实（本仓库）：`src/mini.tsx` 里**完全没有出现 `done`** —— `statusColor` / `statusLabel`（`mini.tsx:89-94`）只处理 `running / queued / error`，其余（含 `idle` 与 `done`）一律落到 `'完成'`（`#6e7789`）。
✅ **并因此产生一个已存在的语义错误**：`mini.tsx:85` 的 `const done = status.agents.filter((a) => a.status === 'idle').length` —— **统计 "完成" 时数的是 `idle`**，而 `idle` 在 `manager.go:151` 的注释是「重启后都是空闲」。即：**一个从没跑过任何任务的 agent 会被计入「完成」；真正 `done` 的 agent 反而没人统计。** 后端 5 态在前端被压成 4 态，且映射错了两个。

🔶 推论：这 5 个状态里**没有任何一个表达「它停下来了，在等人」**。于是在 `mini.tsx` 里：
- 等待权限批准 → 显示 `running` + pulse → 用户以为它在忙
- 等待人来回答问题 → 同上
- 用户离开 10 分钟回来 → 浮层一直 pulse，**没有任何东西提示「3 个 agent 在等你」**

> 🔶 **建议（非实现）**：`Status` 增加一个与 `running` 平级的成员（如 `waiting`），并让它携带一个「一句话原因」。这正是 Claude Code 行摘要与 Warp `Request` 的通知类型所表达的同一件事。

### 4.2 浮层信息密度应当按「层」划分，而不是按「展开/收起」

✅ Claude Code 的三层：footer 计数 → 表格行 → attach。
✅ Warp 的三层：tab badge → mailbox → 会话。
🌐 Apple HIG：popover = 几件相关的事，交互完消失；panel = 占大量空间。
🔶 推论：`mini.tsx` 现在的「52px 岛 / 372px 展开列表」是**两层**，但**两层都太满**：
- 第 1 层（常驻）应只回答「有几个在跑、有几个等我」，即 **2 个数字或 1 个计数**。
- 第 2 层（展开）应只回答「谁在干嘛」，即**每 agent 一行：名字 + 一句话 + 年龄**，不应有 tooltip + 右键菜单 + 输出片段。
- 第 3 层不该在浮层里 —— 点击即 `focusAgent` 到主窗（这条我们现在是对的）。

### 4.3 关系表达：pill bar 而不是树

✅ Warp 的 pill bar + 面包屑，且编排深度**恰好一层**。
✅ ADR-0001 P3 已定「子 agent 侧栏嵌套在父 agent 下方」——这是**主窗列表视图**的形式。
🔶 推论：**两者并存，服务不同密度**：
- 主窗侧栏：缩进嵌套（层级关系一眼可见，适合管理）
- 浮层 / 顶部：pill 条（父在左、子向右，点进原地换 pane、面包屑返回，适合「我正在看谁」）

### 4.4 不要自建通知系统，但要定义「一条通知怎么算」

✅ Devin：*"one notification per session rather than one per surface"*，且 **off by default**。
✅ Warp：`working / blocked / completed / errored` 四态 → **Complete / Request / Error 三种通知类型**。
✅ Claude Code：*"notify only when they need your input"*（`/loop` 会话）；`agent_needs_input` / `agent_completed` 两种 hook 类型。
🔶 推论：通知的**触发条件只应有两类**：`needs_input` 与 `completed`（含 failed）。**`working` 不发通知**；`queued` 不发通知。

### 4.5 「两个展示密度」＝ 一个状态源 + 两个渲染目标

✅ Raycast：菜单栏按钮 toggle 同一个窗口；pinned / screen-share-hide 是同一窗口的附着策略。
✅ Cursor：两个对等窗口，各自保留完整动作集。
🔶 推论（对应「避免做成两个独立应用」）：
1. **状态源唯一**：`miniStatus` 与主窗的 agent 列表必须是同一个投影，不能像现在这样 `mini.tsx` 用 `Sidecar.listAgents()` + `events.miniStatus` 自建一份，主窗另建一份。
2. **一行文案在服务端/状态层算一次**，两个渲染目标共用（现在 `mini.tsx:51-57` 在前端截 100 字符）。
3. **窗口属性（always-on-top / 跨 Space / 录屏隐身 / 失焦不关闭）是配置，不是分支代码。**
4. **升级通道单向且显式**：浮层 → 主窗必须是一个明确的动作（`focusAgent`），反向（主窗 → 浮层）不应存在，否则两个形态互相竞争注意力。

🔶 **一个需要正视的风险信号**：本次调研的 6 个产品中，**没有一个**采用「主窗 + 独立常驻小浮窗（灵动岛/桌宠形态）」作为并发状态的载体。它们全部把并发状态放在**主窗口内的某个区域**（表格、侧栏、tab badge、footer、窗口角落的 toast）。
唯一接近的是 **Raycast HUD**，但 HUD 是**瞬时**的（"automatically hide the main window and show a compact message at the bottom of the screen"），**不是常驻显示 8 个 agent 的状态**。

> 🔶 因此：**「常驻小浮窗」不是行业共识，是一个未经验证的产品赌注。**
> 它的合理性理由（不抢占屏幕、跨应用可见）是成立的，但**必须自己承担**这些成本：window 管理层级、点击/拖动冲突（`floating-window-review.html` 已记录）、失焦行为、多显示器、Space 切换、录屏可见性、`prefersReducedMotion`。
> 可参考的折中：**Raycast Notes 的附着策略**（menu bar toggle + pinned 跨 Space + 录屏隐身）比重新发明一个常驻岛更便宜。
