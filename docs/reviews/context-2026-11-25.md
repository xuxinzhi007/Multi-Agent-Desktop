## 3. 已冻结的关键决策

1. **`Runtime` 与 `Backend` 分离**
   - `Backend` 仍是 loop / mock / supervisor / doubao（模型与内核）。
   - `Runtime` 是 `native` / `acp`；`Runtime=acp` 时覆盖 backend；缺省按 native。
   - 老 `agents.json` 不需要迁移。
2. **ACP 一轮一个子进程**：轮末 `Close`，停止与删除都杀进程组；不做长期常驻进程复用。
3. **前端只认旧事件**：ACP/native 都映射回 `agent.delta` / `agent.reasoning` / `agent.tool` / `agent.message` / `agent.stopped`；不新增事件类型。
4. **审批唯一入口**：`approval.Center`，ACP 的 `permission.request` 也必须经过它；超时/关闭按拒绝，不自动放行。
5. **ACP 首版能力边界**：只发文本，不带附件/图片；plan / usage 事件暂不显示。
6. **协议版本 `mad.runtime/1`**：只增不改；未知事件降级 notice；`SessionID` 用本地 agent id。

## 6. 助手化调研结论

### 6.1 OpenClaw 的真实骨架

不是「一个更聪明的模型」，而是 **Gateway + Runtime + Tools + Skills + Memory + Heartbeat**：

- **Gateway**：常驻控制面，接渠道、路由消息、管会话、限流；默认只绑 `127.0.0.1`。
- **Runtime**：把 `SOUL.md`（人格）、`USER.md`（用户偏好）、`MEMORY.md`（长期记忆）、`AGENTS.md`（工作区规则）、skills、历史拼成系统提示。
- **Memory**：`MEMORY.md` + `memory/YYYY-MM-DD.md` 日记，混合检索召回；不是把所有聊天无差别塞进上下文。
- **Heartbeat**：后台定时唤醒，没事就回 `HEARTBEAT_OK`，Gateway 识别后静默丢弃，避免刷屏。
- **Skills**：`SKILL.md` + ClawHub 生态；**Docker 沙箱**跑会话。
- 渠道数量是它的规模优势（20+），也是它的维护负担与攻击面。

<RichMediaReference>["https://learnopenclaw.org/architecture.html","https://freeopenclaw.io/what-is-openclaw","https://www.harnesses.sh/?autonomy=supervised&license=open-source&local=yes"]</RichMediaReference>

对我们的启示：**渠道不用多，Gateway / 记忆分层 / 心跳静默这三个机制必须做对。**

### 6.2 同类项目，各自可借鉴什么

| 项目 | 定位 | 可借鉴 | 不建议照搬 |
|---|---|---|---|
| OpenClaw | 渠道优先的个人助理 | Gateway、SOUL/USER/MEMORY/AGENTS 文件、Heartbeat、Skills | 20+ 渠道、默认 Docker、庞大的第三方技能生态 |
| Letta（MemGPT） | 有状态记忆 Agent | 分层记忆块、可编辑长期记忆、按需换入上下文 | 整套运行时移植 |
| Hermes | 自我整理记忆 | 记忆/技能自动积累与淘汰 | 自学习闭环的复杂度 |
| NanoClaw | Claude + 容器 | 每会话容器隔离 | 强绑定 Claude |
| PicoClaw | 小硬件 | 低资源常驻、精简依赖 | 功能裁剪过多 |
| Nanobot | 小代码库 | 单进程、少依赖的网关形态 | 功能面太窄 |
| OpenHands | 软件工程 Agent | Docker 沙箱、任务队列、PR 流程 | 重量级平台 |

### 6.3 记忆：先用 SQLite，不要先上向量库

调研里最一致的做法是：

- **原始事件逐条存**，不要入库前就抽取摘要；抽取丢掉的细节，检索时找不回来。
- **SQLite FTS5** 做关键词召回，`sqlite-vec` 可选做语义召回，RRF 融合两路结果；没有 embedding 时优雅退化为 FTS。
- **三层**：日记（原始）→ 事实（带来源、时间、置信度）→ 长期（人工/自动固化）。
- **可追溯**：每条记忆带来源（谁、哪个渠道、哪次会话）与 `valid_from` / `valid_to`；纠正用「关闭旧事实 + 链接新事实」，不直接删。
- **整理是后台任务**：定时把日记收成事实、去重、归档；不在每轮对话里做。

<RichMediaReference>["https://arxiv.org/pdf/2605.04897v1","http://www.shturl.cc/14a96c366d3933cf4cde953fbc65477a","http://www.shturl.cc/074ef4db2ecd2210a3a6340a370afb45"]</RichMediaReference>

落地建议：`internal/memory` 用单文件 SQLite（WAL），表：`events`、`notes`、`facts`、`facts_history`；先只做 FTS5，`sqlite-vec` 留作开关。工具暴露 `memory_search` / `memory_write`，写入必须带来源。

### 6.4 渠道

| 渠道 | 可行性 | 说明 |
|---|---|---|
| 飞书 | 已有 | 多机器人长连接、审批卡、群聊，继续用 |
| Telegram | 高 | Bot API 长轮询，无需公网回调；适合先跑通第二渠道 |
| Discord | 中 | Gateway 需要常驻连接；群/频道映射要设计 |
| 企业微信 / 公众号 | 中 | 合规、可回调；比个人微信稳 |
| 个人微信 | 低 | hook 方案封号与合规风险高，不建议 |

### 6.5 调度与心跳

- cron / interval / 一次性任务统一进 `scheduler`，与用户回合共用队列和审批。
- 心跳结果用固定 token（如 `HEARTBEAT_OK`）表示「无事」，网关丢弃。
- 静默时段、每任务频率上限、连续失败降频，三者缺一不可。
- 主动任务默认只读；要写文件必须显式 `allowWrite`。

### 6.6 安全边界

- 渠道消息是**不可信输入**：不能拼进系统提示；工具调用必须过审批。
- Gateway 默认只绑 localhost；远程走 Tailscale / SSH 隧道。
- 审批审计要记「批准人 + 来源渠道」；当前审计缺批准人（P1-5）。
- 常驻进程权限高于手动操作：默认 `ask`，只读自动。

### 6.7 部署

- N100 / Debian + systemd + Tailscale 是最贴合现有硬件的形态。
- 单写者：`agents.json` / `gateway.json` / `schedules.json` 只允许网关写；桌面远程模式只读。
- 密钥用 systemd `EnvironmentFile` 或环境变量，后续再迁钥匙串。
