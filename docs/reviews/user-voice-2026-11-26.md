## 1. 逐案复盘

### 案例 1｜同一个问题收到两条回复

- **我期望**：一张卡，过程在里面长，结论落在同一张卡上。
- **实际**：`send(...)` 先发一条完整答案，再把进度卡 `paint` 成「已回复」→ 我的列表里两条。
- **证据**：`internal/feishu/service.go:497-508`（先 send 再 paint）、`:82`（`repliedLine = "已回复"`）；
  注释自陈"答完另发一条，群里才会有提醒"——为了群提醒牺牲了单聊观感。
- **我的原话**："好像是回复了两次。"
- **严重度**：P0（第一眼就错，且发生在最轻的一句提问上）。
- **频率**：每条任务都这样。

### 案例 2｜它读错项目，而且不告诉我边界在哪

- **我期望**：我提 `data-service`，它先去确认哪个根里有这个仓库，再回答。
- **实际**：它在 `multi-agent-desktop` 的提交上作答，语气还很确定。
- **证据**：`internal/agent/loop_backend.go:456-463` 的 `workspaceRootLine` —— 多根时**只写目录基名**
  （`工作区根：multi-agent-desktop、data-service`），不给绝对路径；模型只能猜哪个基名对应哪个仓库。
- **我的原话**："你当前不是 data-service 项目，是不是读取不到呢？"
- **严重度**：P0（答错比答不出更贵，我得重新解释一遍）。
- **频率**：每次跨仓库提问。

### 案例 3｜多根能力已经有了，但我在界面上找不到

- **事实核对**：`Roots`、`ExtraDirs`、`bash` 的 `cwd` 参数、`Resolve`（相对路径在主根找不到时逐个附加根试）
  都已经实现（`internal/workdir/roots.go`、`internal/tool/builtin/builtin.go:96-108`），
  注释里还对标了 Claude Code 的 `--add-dir`。**这个功能是通的。**
- **我的实际体验**：我不知道有这个开关。入口藏在 `AgentView` 的 `ExtraDirs` 面板（`AgentView.tsx:1488-1533`），
  会话里没有任何空状态提示"你可以再加一个根"。
- **结论**：这条不是"缺功能"，是"**功能不会被发现**"。可发现性的成本比再写一个功能低一个数量级。
- **严重度**：P1。

### 案例 4｜插话不是插话，是排队

**状态（2026-11-26 晚）：已修。** 后端 loop 侧已有 `SteerCh`/`Steer`：`enqueue` 时给正在跑的一轮发信号，
工具批次被取消、已完成的工具结果保留，新消息在**下一个回合**并入历史（`internal/loop/loop.go:411-450`、
`internal/agent/manager.go:enqueue`、`loop_backend.go:276-286`）；前端不再另排队，发送即乐观插入并按发送时刻盖章
（`useBackend.ts` 的 `agent.prompt` 分支）。护栏：`internal/loop/interrupt_test.go` 5 条。



- **我期望**：任务跑到一半我补约束，它在下一个工具调用前看到并改方向。
- **实际**：`agent.prompt` 发现 busy 就把文本塞进 `outbox`，等这一轮结束/出错才补进消息列表。
- **证据**：`src/lib/useBackend.ts:658-667`（busy → `outbox`）、`:388-407`（出错时才 flush，
  且 flush 时用 `Date.now()` 盖章）。
- **副作用**：补进来的那条**盖的是 flush 时间**，所以它永远排在答案后面 —— 这直接制造了案例 5。
- **严重度**：P0（长任务里这条最贵，等于我只能"看着它跑错"）。
- **频率**：只要有长任务就发生。

### 案例 5｜历史消息排到新消息后面

**状态（2026-11-26 晚）：已修。** 排序收敛到唯一入口：`src/lib/message.ts` 的
`sortAgentMessages` / `sortChannelMessages`（按时间升序、同时间戳保持到达顺序），
`useBackend` 在每个消息更新点（事件回推 / 历史拉取 / 补拉 / 乐观插入）统一走它。
护栏：`e2e/message-order.spec.ts`。



- **我的实际体验**：切回一个会话，昨天的对话跑到今天后面去了；插话补进来的那句也排在答案后。
- **证据**：消息列表全程 append-only，没有任何按时间归并：
  - 会话：`src/lib/useBackend.ts:678`、`:405-407`（`[...(a.messages ?? []), msg]`）
  - 频道：`src/lib/useBackend.ts:571`（`[...(ch.messages ?? []), msg]`）
  - `AgentView.tsx` 渲染时也未见排序（`timestamp` 只用于算耗时/显示时钟，`:630`、`:2012`）
- **为什么被忽略**：拍平追加在"消息只按顺序到达"的假设下是对的，一旦有补拉/排队就不成立。
- **严重度**：P0（一眼错；而且它会污染对案例 4 的判断，让我分不清是没插进去还是插错位置）。
- **频率**：每次切会话 + 每次插话。

### 案例 6｜频道一个样、会话一个样

- **实际**：频道是卡式消息（`ChannelView.tsx`，1022 行），会话是气泡（`AgentView.tsx`，2313 行），
  两条渲染路径、两套排版、两套"头像/时间/复制"处理。
- **我的感受**：同一个 agent，在两个地方像两个人。我不关心是哪个组件，我只关心"我说的话和它说的话"长一个样。
- **严重度**：P2（不改功能，但每次切换都在掉信任）。

### 案例 7｜桌面处理完了，网页还挂着那张卡

**状态（2026-11-26 晚）：已修。** 两侧都补了：SSE 加 `id:` + `Last-Event-ID` 续传（broker 保留 256 条），
外加三条快照对账（`gateway.connected` / 窗口聚焦 / 「已失效」即收卡）。
详见 `docs/troubleshooting/known-issues.md` #23。

## 3. 我作为用户的真实感受

**顺手的地方**（这些别动）
- 一句话进去，它真的会自己拆步骤、调工具、跑 verify，不用我写"先读再改"这种规矩；
- 审批卡能在群里就地收尾，手机上点一下就过；
- 记忆是真共享的（私聊说过的，群里接得上），这点比看起来重要。

**别扭的地方**
- 它不笨，但**边界不透明**：我不知道它能碰哪些目录、群历史有没有、我这句话是排队还是生效了。
  边界不清时，我的默认策略就退化成"少用它、关键事自己来"。
- **每次都要重新校准信任**：一个"已回复"的空卡、一条排错位置的消息，都会让我怀疑后面所有结论。

**不敢用的地方**
- 长任务中途改需求。因为插话=排队，我宁可先 `/stop` 再重来——这等于把它的"协作"能力废掉了一半。

## 4. 如果只能改三件（按我作为用户的排序）

1. **消息按 `ts` 归并**（0.5 天）——一眼错的东西必须先修，否则后面所有体验改动都无法验收。
2. **插话变收件箱检查**（1–1.5 天）——每轮工具调用之间读一次新消息，命中就重排剩余计划。
   这是"能和它一起干活"和"只能给它派活"的分界线。
3. **飞书一条卡**（1 天）——过程与结论同一张卡，审批就地收尾。

紧接着值得做的（便宜且立刻可感）：

5. **工作区根在提示里给绝对路径 + 会话空状态一行"可再加一个根"**（0.2 天）。
   功能已经在了，只差让人知道。
