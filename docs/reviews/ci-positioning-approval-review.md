## 1. 第 3 点：CI 与提交卫生

详细版在 [`ci-commit-hygiene-plan.md`](ci-commit-hygiene-plan.md)，这里只留结论，避免两份文档打架。

三句话：

1. **门禁脚本早就写好了**：`package.json` 里的 `verify` = typecheck + `go vet` + `go test -race` + e2e。缺的是自动触发——仓库没有 `.github/`，没有 `.githooks/`。
2. **现在接 CI 会立刻红**：全量 `go test ./...` 有 1 个失败，`internal/llm/TestContextLimitUsesWindowOrProvider` 期望 4096、实现返回 8192，测试和代码已分叉。这条必须先决策（谁是对的），不能靠改测试让它变绿。
3. **全量 2m46s**（`internal/agent` 165s、`internal/llm` 127s），所以 pre-push 只能跑 13 个快速包，全量留给 CI。

另外两个会被忽略的细节：`.oxlintrc.json` 在但 oxlint 没装；`tmp-gp-context-lab/` 被 gitignore 但 `go test ./...` 仍会扫进去，CI 要用显式包路径。

提交切分方案（23 条改动 → 4 个提交，按测试/后端/前端/依赖分组）和两个钩子脚本的完整内容都在那份文档里。

## 2. 第 4 点：产品定位

### 2.1 两个候选

- **A. 本机多 agent 并行开发工作台**：开 N 个会话，各自独立目录/worktree、并行跑、随时插话和停止。
- **B. 飞书里的值班排障 copilot**：在群里被 @，认领任务，跑完回卡片，写操作回卡片审批。

现在这个产品**同时是两者**，而 `design.md` 自己标着：是否收窄为 B “还没定，不要当结论用”。

### 2.2 我的判断：A 是产品，B 是遥控面

理由三条，都不是偏好问题：

1. **最值钱的资产只有 A 形态用得上。** 项目真正的差异化在 `internal/loop`：停止、预算、检查点、中途插话这四个控制点。这些是“人坐在本机、同时盯 N 个 agent”才需要的能力。B 形态里用户看到的是进度卡和审批卡，四个控制点一个都用不到。
2. **B 不是差异化能力，是渠道。** 你们自己的调研结论是同赛道 14 个竞品没有一家支持飞书。这说明飞书不是“别人做不到”的地方，而是“在中国办公场景里确实有人这么用”的渠道。渠道值得做，但不该反过来定义产品内核。
3. **当前的审批 bug 就是定位漂移的症状。** 为了“飞书里也能用”，审批被做成 app 卡 + 飞书卡两条路径，而归属关系没建起来，于是子会话的卡直接掉地上（见第 3 节）。功能是照定位加法加出来的，缺陷也是这么加出来的。

### 2.3 收窄之后，飞书侧只做三件事

发任务、看进度、批写操作。不做第四件——尤其不做“飞书里再长出一套会话管理/知识库/技能”。

### 2.4 判定线

定一条能自我检查的线：**下一个季度，飞书侧的功能增量不得超过本机侧。** 超了就是漂了，不是“用户需要”。

### 2.5 反方意见（值得听）

有一种说得通的反对：“我平时就在飞书里，工作台打开率低，收窄等于自断用户。” 这个说法成立的前提是**用户主要在手机上**。如果是，那 A 形态本来就不该是主战场，应该直接做 B，并把 loop 的四个控制点降级成后台能力。所以这不是技术判断，是“你的真实使用场景在哪”的判断——这个只有你能答。

## 3. 第 5 点：权限管理评估

### 3.1 结论

不是“子 agent 的卡没显示”一个 bug，是审批模型缺三个字段（归属、来源、批准人），由此长出四类问题，其中一个是**直接越权**。

### 3.2 五个问题，按严重度

**P0-1 谁能点批准，完全没有校验。**
`internal/feishu/service.go:798` 的 `decide(cfg, Turn)` 只取 `ActionID` 和 action，`Turn.Sender` 拿在手上但没参与任何判断。卡片是发在群里的——**群里任何人都能点“本会话允许”，真的放开这台机器的文件写入和命令执行**。这比丢卡严重得多。

**P0-2 子会话的卡在飞书里静默消失。**
`Ask` 遍历 `s.runs` 时条件是 `cur.agent == v.AgentID`，而 `runs` 只登记“正在回答这条飞书消息的会话”。`delegate` / `Supervisor` 派生的子会话名不含“的协助”，不会被认领，匹配失败直接 `return`——无日志、无通知、无降级。用户在飞书里只能看到子任务“莫名失败”。

**P0-3 必然超时。**
`approval.Center` 固定 5 分钟；Supervisor 子会话跑 10 分钟、父等待 20 分钟。子会话的卡一出现就已经注定 5 分钟后被 denied。

**P1-4 授权记忆粒度错位。**
`allowed` 是 `map[agentID]map[toolName]`：父会话批准过 `bash`，子会话还再问一遍；子会话的“本会话允许”独立存在，直到删会话才 `Forget`。而 `bash` 一旦被记住，后续任何命令都不再问——**一次批准等于永久放行**。

**P1-5 审计答不出“谁批的”。**
`audit.jsonl` 里有 agent、tool、status、exit_code、耗时，没有批准人、没有来源（桌面/飞书）、没有等待时长。

### 3.3 修复设计（七条，不改代码）

1. `ApprovalView` 补三个字段：`RootAgentID`、`Origin`（app/feishu/chat）、`DecidedBy`。现在只有 `AgentID`，UI 和飞书都没法表达“这是谁在申请”。
2. 路由改成归属解析：`ResolveApprovalRoute(agentID)` 沿 `ParentID` 上溯最多 3 层找已登记的 run，命中就发卡，标题写“子会话 X 申请 · 工具 Y”。
3. 找不到时**降级而不是静默**：写审计 + 往主会话所在对话发一条非阻塞文本（“子会话 X 需要批准一次写入，请在桌面处理”），同时 app 内卡片高亮。
4. 超时跟随运行：子会话对齐到 20 分钟，或跟随所属运行的剩余时间。
5. 记忆沿父链继承，`bash` 永不参与 remember。
6. 批准人校验：卡片回调拿 `Turn.Sender` 比对会话 owner 或显式允许名单，不匹配就拒绝并回“你没有这个会话的审批权”。
7. 审计补 `decided_by` / `origin` / `latency_ms`。

### 3.4 验收用例（每条都能写成 e2e）

1. 子会话发写操作 → 飞书出现一张标注“子会话 X”的卡。
2. 子会话所在的 run 不存在 → 桌面有卡、飞书有一条文本通知，不静默。
3. 子会话跑 10 分钟的任务 → 不因 5 分钟审批超时被 deny。
4. 非 owner 的群成员点“允许” → 拒绝，并回一条权限提示。
5. `bash` 批准过一次后，第二次仍然弹卡。
6. 父会话允许 `write_file`，子会话继承；父允许 `bash`，子会话不继承。
7. 桌面已经处理过 → 飞书按钮收起（这条现在就有，别改坏）。
8. `audit.jsonl` 里能看到批准人和来源。

### 3.5 一个容易被忽略的文案问题

卡片按钮写“本会话允许”，用在子会话身上指的是子会话，用户几乎一定理解成主会话。要么改文案为“本子会话允许”，要么在卡上显示归属。

## 4. 论文借鉴：三篇，各治一个病

**MAST（Multi-Agent System Failure Taxonomy，arXiv:2503.13657，NeurIPS 2025）**
7 个框架、200+ 任务、14 种失败模式，归为规格问题 / agent 间失配 / 任务验证三类。对本项目直接对得上的三条：步骤重复 15.7%（`repeatLimit=3` 正对应）、无或不完整验证 8.2%（缺任务级完成证据）、不知道终止条件 12.4%（Supervisor 父等 20 分钟但子会话没有终止语义）。
**借什么**：把 14 条失败模式当 e2e 的靶子，一条写一个可复现 spec，比凭空想用例靠谱。
**不借什么**：它的 LLM-as-a-judge 自动标注管线，那是为大规模评测准备的，本项目没有那个量。
<RichMediaReference>["https://arxiv.org/abs/2503.13657v2"]</RichMediaReference>

**Progent（Programmable Privilege Control，arXiv:2504.11703）**
把权限表达成“工具名 + 参数”的符号规则，每次调用确定性检查；策略更新由 SMT 判定是收窄还是扩张，扩张必须人工批准（monotonic confinement）。
**借什么**：两条原则——规则要带参数、默认只允许单调收窄。这正好治本项目“按工具名记忆”和“子会话权限不沿父链收窄”两个病。
**不借什么**：不必真引 SMT 求解器，`bash` 的参数空间用规则表达不了那么精确，硬上会得到一个算不动的东西。
<RichMediaReference>["https://arxiv.org/pdf/2504.11703v3"]</RichMediaReference>

**CaMeL（Defeating Prompt Injections by Design，arXiv:2503.18813，SaTML 2026）**
控制流与数据流分离 + capability，让不可信数据无法影响程序流，也不能把私有数据经未授权通道外泄。AgentDojo 上 77% 任务可证明安全（无防御 84%）。
**借什么**：认知——system prompt 里那句“工具输出是数据不是指令”属于提示词层防御，可以被绕过，结构性的做法是给工具调用标数据来源，来源不可信且要动写操作时强制提级。
**不借什么**：双 LLM 解释器架构，成本对本项目过高。
<RichMediaReference>["https://arxiv.org/abs/2503.18813?context=cs"]</RichMediaReference>

**AgentDojo（NeurIPS 2024）** 可以直接当安全 regression 基准，把提示注入攻击成功率做成每月跑一次的 spec。

## 5. 新发现：截图里的“默认追加”

截图对应当前 `HEAD` 版本（`AgentView.tsx:845` 那句“写下一句会排到后面”），而工作区未提交的改动已经把这句改成“发出去会在下一步之前插进当前任务……”。所以**先重新构建再复现**，否则测的是旧行为。

三种可能，修法完全不同：

**A. 回复结尾总追问“是否开始 / 需要我继续吗”。**
代码里没有这句硬编码，是模型自己生成的。`loopSystemPrompt` 第 4 条只禁止“让我先”这类过程句，没禁止结尾追问。软约束是加一句“不要以‘是否开始’结尾，能做的直接做”；硬约束是在 loop 迭代边界判断“本轮只有文字、无工具调用、且以问句结尾”，自动插 system 提示继续跑。后者更接近 Claude Code 的做法，也更适合无人值守。

**B. 旧消息被追加到新消息下面 / 新消息插到顶部。**
截图时间顺序是 19:43:55 → 18:33:03 → 18:27:21 → 18:30:27，两种排序都不成立。`AgentView` 直接按 `rawMessages` 顺序渲染、不排序，顺序取决于后端 `Messages` 的写入顺序；而 `Sync` 每轮用 `out.Messages` 整体覆盖 `a.Messages`，从检查点续跑时若 `out.Messages` 比历史短，覆盖就会产生错序。

**C. 每条消息下方固定出现“知识库（1 条命中）”。**
这是默认行为不是 bug。觉得吵可以改成只在打开知识面板时显示。

定位方法：把工作区改动构建一版，用同一个会话复现一次，看时间戳是否仍然乱序；如果是 A，直接看那一轮有没有工具调用事件（`agent.tool` 为空就证明它在纯聊天里停下来等确认）。

## 7. 需要你拍板的四件事

1. **`ContextLimit` 到底是 4096 还是 8192？** 这决定测试改哪边。
2. **定位收窄到 A 还是 B？** 或者接受“A 为主、B 只做三件事”。
3. **审批身份策略**：飞书卡片只允许会话 owner 点，还是允许显式白名单？群场景要不要保留“@ 机器人的人”作为批准人？
4. **`bash` 要不要单列成高危工具**：永不 remember、默认不进 auto 的自动放行。

这四条定完，前三条技术方案就可以直接开工，不用再来回确认。
