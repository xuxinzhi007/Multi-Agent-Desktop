NotesForSystemPrompt 只是一个 Query + strings.Join 的 adapter。删掉它，复杂度不会消失，只会搬到 Manager 里 —— 它没通过 deletion test。

After · 一个 deep module

1 : 6

fileStore / memoryStore 保留在 interface 里 —— 两个真实 adapter，seam 成立。但 选哪些、怎么渲染 收进同一个 module。

Problem

选笔记的策略（谁可见、多少条、什么顺序）散在 main.go 的 knowledgeProvider 和 agent.systemPromptFor 两处，两处都在 internal/knowledge 之外。

Solution

在 knowledge 里加一个 View：入参是 agent 的 (id, role, backend)，出参是「渲染好的 prompt 段 + 命中的 Note ID」。删除 knowledgeProvider，agent 依赖收窄成 View。

Wins

  • · locality：注入策略一处改，五个触发点全跟
  • · leverage：一个 View 承担 Create / attach / Preview 三个调用点
  • · 删除 knowledgeProvider 与 maxKnowledgeLines
  • · interface is the test surface：TestSystemPromptFor 的表驱动用例直接下移到 knowledge

注意

这会让 internal/agent 反向 import internal/knowledge。要么接受（agent 已经 import llm/cli，无循环），要么把 View 定义成 Note 的纯函数、让 Sidecar 渲染。前者更 deep，后者更松。这是唯一需要你拍板的点。

2 · attach 泄漏进 history：service 层自己拼 note 到 agent 上

main.go:511 AttachNoteToAgent · internal/agent/manager.go:667 AppendSystemMessage

Strong in-process

Before · 注入写进消息流

After · history 只放对话，note 每轮现算

Problem

AttachNoteToAgent 在 service 层做三件业务事：全量扫 store 找 note、渲染、往 agent 的 Messages 追加 system。它绕过 KnowledgeProvider 这条唯一的 seam，也不写 Scope、不记「哪个 agent 引了哪条」。

Solution

给 Agent 加一个引用集合 Knowledge []string（走已有 4 处白名单：Save/Load/Snapshot/viewMap），AppendSystemMessage 删除。注入只发生在 executeMock/executeCLI 组装 history 的那一行。

Wins

  • · locality：note 的可见性收敛到 View，不再有第二条路
  • · attach 变幂等：重复 attach 不复制 history
  • · 删除笔记立刻生效，不用重建会话
  • · leverage：UI 上的 "已注入 N 条" 直接读 Agent.Knowledge

接口形状（不写代码，只定形）

Attach(agentId, noteIds []string) → AgentView
Detach(agentId, noteId) → AgentView
— 两者都是「改引用集合」，不碰 Messages

After · 三种 scope，一个解析函数

ScopeGlobal

所有 agent · 受预算约束

ScopeAgent(id)

只有该 agent · 不占全局预算

ScopeChannel(id)

频道成员 · 广播时生效

渲染顺序：agent 私有 → channel → global。同一 key 后者覆盖前者。

Problem

UI 的 select 允许用户选「仅 Agent X」，Note.Scope 被写进 JSONL —— 然后没有任何读取路径会用上它。用户以为写了一条私有约定，实际它永远不生效。

Solution

View(agent) 按三层 scope 取并集、去重、排序。Query.Scope 保持精确匹配语义不动（它是 store 层的 primitive），解析放在 View。

Wins

  • · 承诺与行为对齐，UI 不再说谎
  • · 「这个 agent 专属的自定义指令」成为真实能力
  • · 为 #4 的相关性筛选提供天然分区

向后兼容

现有 knowledge.jsonl 里 scope 为空或 agent ID，两种都是新语义的子集，无需迁移。旧的 TestQueryFilters 的 scope 用例保持绿。

4 · 固定 top-8：知识库长到 200 条时，注入的是最近写的 8 条

main.go:932 maxKnowledgeLines · knowledge.Query 线性扫描

Worth exploring in-process

Before · 无排序，无相关度

200 条笔记 · 插入序 · 截断取前 8

1 2 3 4 5 6 7 8 … 200

第 200 条（昨天刚写的关键约定）被丢弃。
判据是「写入早」，不是「相关」，也不是「重要」。

After · 相关性 + 分档预算

同一份数据 · 按 agent / 最近对话打分

r r t t s 8 200 …

必选：scope 命中（agent / channel）

相关：tags 命中最近 3 轮文本

兜底：最近写入，填满预算

Problem

Query 只支持精确 scope、AND 标签、子串匹配、截断；排序就是插入序。谁被注入完全由写入时间决定，而 maxKnowledgeLines 是个魔数，没有 token 概念。

Solution

把「选几条」从条数改成字符预算，按三档排序后贪心填充。View(agent, recentText) —— recentText 由调用方从最近消息里取，View 保持纯函数。

Wins

  • · 关键约定不会因为写得晚而消失
  • · prompt 大小可预测（字符预算 vs 条数）
  • · locality：排序规则只有一个实现，可单测

为什么不推荐先做向量检索

笔记规模是「人写的几十到几百条」，标签 + 子串 + 时间已经足够。引入 embedding 会把一个 nil 依赖的纯内存 module 变成需要外部服务的 adapter —— 在笔记真的上千条之前，这是负的 depth。

Problem

executeCLI 调 runner.Run(ctx, text)，text 是这一次的 prompt，会话 history 和知识库都不参与 —— CLI agent 实际上是个无状态单轮调用，而 UI 表现得它有记忆。

Solution

CLIRunner.Run 的入参从 string 改成 Request{System, History, Prompt}。claude -p 支持 --append-system-prompt，history 拼进 -p 正文。Channel 广播复用同一个 assemble。

Wins

  • · 三个后端共享同一份「agent 看到了什么」
  • · leverage：assemble 一个函数服务 3 个 adapter
  • · 可测：assemble 是纯函数，直接快照比对

注意

这是本报告里 唯一会改变外部行为 的一项 —— CLI agent 的输入变长，token 成本和输出风格都会变。建议独立于 #1~#3 提交，单独验证。

6 · note.attach 看不见，也没有 Detach

Sidecar.AttachNoteToAgent → AgentConfig.Emit（只有 AgentView）

Speculative in-process

Before · 单向，无回读

After · 引用是一个可见集合

AgentView.knowledge

  [ "部署约定" ✕ ]

AgentView 头部多一行 chip，和现有的 📁 / ✦ 两个 chip 同构。

Wins

  • · attach 变成可逆操作
  • · interface is the test surface：AgentView 是唯一事实
  • · 复用 #2 的 Knowledge []string，零新增状态
  • · 用户第一次能看出 agent 在按什么规则回答

为什么是 Speculative：它是 #2 的 UI 后置项，本身不解决摩擦，只是把 #2 的 depth 暴露出来。等 #2 落地后再决定要不要做。

Top recommendation

先做 #2，再做 #1

#2 是唯一一处「已经产生错误行为」的地方：AttachNoteToAgent 把笔记写进 history，删不掉、看不见、还绕过了唯一的 seam。 把它换成 Agent.Knowledge []string 之后，#1 的 View(agent) 才有确定的输入 —— 先修数据形状，再收拢 interface。 这两项做完，#3 的 scope 解析和 #4 的排序都只是 View 内部的事，#6 自然免费。
