## 1. 需求（可直接当提示词用）

```
飞书是这个桌面 Agent 的主要入口之一，但现在的交互是按功能堆出来的，不是按"一次对话"设计的：
一个问题会留下两条消息（进度卡写成「已回复」+ 另发一条答案），审批卡批完不消失，
失败只剩一行错误，答案长了会被截断，用户问"昨天群里那条通知"时它答不上来。

请以"一个回合 = 一条消息"为总原则，重建飞书侧的会话体验：

1. 一个回合只留一条可见消息。进度、答案、失败、停止都在同一张卡片上就地演进，
   不再出现"空泛的已回复 + 真正的答案"两条。
2. 群聊默认**不 @ 也要应答**（现在是 MentionOnly，只有被 @ 或被回复才回答，
   见 service.go:421）。但不能一刀切关掉——群里每条闲聊都会变成一次模型调用。
   请做成群级三态：off（不理）/ mention（只 @，保留现状）/ active（不 @ 也应答），
   active 只对已绑定 agent 的群开放，并配护栏（见方案 §3）。
3. 审批卡与执行卡分离：审批卡批完就地改成"已批准 / 已拒绝（谁批的、几点）"，不再另发；
   执行卡继续显示后续进度。
4. 失败要可读：卡片变红，一句人话原因 + "重试"，而不是 err.Error() 原文。
5. 长答案不截断：超长时分段更新同一张卡片，或折叠成"展开全文"。
6. 历史可检索：能拉到群里已有的历史消息（例如昨天的 review 通知），
   用户追问时能引用，而不是反问"给我链接"。

约束（不可破坏）：
- 不改变审批的归属语义（owner + 白名单仍是唯一判定），不改变审计记录（audit.jsonl 字段不动）。
- 不改桌面端与内嵌网关的既有行为，只动飞书这一侧的表现层。
- 每一条改动都要带测试；现有断言若与新行为冲突，改断言并在测试注释里写明原因。
- 现有 /stop、审批卡按钮、图片输入能力保留，不新增第二套卡片模板。
```

## 2.5 单聊与群聊：哪些必须一样、哪些必须不一样

结论：**"人"和"呈现"必须一样，只有"触发"和"提醒"必须不一样。**

| 维度 | 现状 | 应该怎样 |
|---|---|---|
| 人格 / 记忆 | 记忆按 `agentID` 写入（`memory/bridge.go:106`，不含渠道）→ **其实已经共享** | 保持共享；群里回答不该"装不认识"私聊里说过的事，应主动引用 |
| 提示词 | **每次都加** `taskLead = "这是从飞书来的一件任务…"`（`service.go:456`、`:463`） | 只有"转发的通知 / 被动任务"才加；用户直接打字时按对话处理。这是群聊和单聊"像两个人"的主因 |
| 呈现 | 双载体：卡片（进度）+ 新消息（答案） | 统一成一张卡片，进度→答案就地演进，两处一致 |
| 上下文 | `join`（群历史拼进上下文）只在群、且 `!MentionOnly`（`:461`） | 保留 scope 隔离（群内容不能贴到私聊、私聊也不能贴到群），但拼装规则要对齐成一套 |
| 触发 | 群要 @（`MentionOnly`）；单聊直接进 | **必须不同**：群走三态 off/mention/active；单聊永远应答 |
| 提醒 | 群靠"发新消息冒泡"；单聊不需要 | **必须不同**：群用 reaction / @ 提问人；单聊静默 |
| 审批 | 一致（同一队列、同一归属） | 保持，并让审批卡就地收尾 |

## 2.6 应用提示 vs 结构化标记（为什么 `taskLead` 应该删）

提示分三类，主流只在前两类用力，第三类越少越好：

| 类型 | 放什么 | 生命周期 | 现状 |
|---|---|---|---|
| **系统提示** | 稳定规则（"飞书里的一句是一件任务，回复写回原卡片"） | 一次，进缓存前缀 | 已有：`loop_backend.go` 的 `if feishuOn { … }` |
| **结构化标记** | 来源 / 渠道 / 群名 / 附件 / @ / thread | 每条消息，元数据字段 | 已有：`PromptRequest{ChannelID, ChannelName, Context, Images}`（`manager.go:1045-1057`） |
| **每条消息的自然语言复述** | `taskLead`「这是从飞书来的一件任务…」 | 每条，挤占预算、破坏前缀、改语气 | **冗余，应删**（`service.go:80/456/463`） |

关键证据：`loop_backend.go` 的系统提示里已经写了「飞书里的一句是一件任务，用这台电脑上的工具去做，回复会写回原来那张卡片」，
同一件事又被 `taskLead` 每条复述一遍——这正是该文件自己注释里反对的做法
（"两边都写一遍等于每轮让模型读两遍同一件事，白占上下文预算"）。

删掉之后需要保证的只剩一件：**回复仍落在卡片上**。这由系统提示 + 回复载体的实现承担，不靠每条前缀。
若删后发现模型开始"只在正文写答案、不走回复通道"，正确做法是**把一句话加回系统提示**，
而不是回到每条消息前面拼字符串。

## 3. 方案：两批做

### 群聊 active 模式的护栏（不 @ 也应答的前提）

不 @ 也应答 = 群里每条消息都进任务队列。没有护栏，这不是体验优化，是把群变成噪音源。
最小护栏（4 条，缺一条就不该开 active）：

1. **群级开关**：只有用户显式打开 active 的群生效，默认 `mention`。配置落到 `hub` 的群配置里。
2. **忽略规则**（便宜、先做）：自己发的消息、纯表情 / 单字 / `+1`、系统消息、其它机器人发的消息，一律不进队列。
3. **同群串行 + 限速**：同一个群同时只跑一轮（后到的排队或合并），每群每分钟不超过 N 轮；
   超限时不丢消息，回一句"今天这条我先记下，等前面跑完"。
4. **静默开关**：`/mute 1h` 临时闭嘴，`/unmute` 恢复；active 群里默认不 @ 任何人，避免刷屏。

### 第一批（1 天，直击"回两次"）

1. **一条消息原则**：`service.go:497-508` 的收尾统一走 `paint(final)`；删掉 `repliedLine` 分支与常量。
   群聊的提醒改用 reaction（`im/v1/messages/{id}/reactions`）。
2. **审批卡就地收尾**：`decide()` 成功后 patch 原卡为「已批准/已拒绝 + 谁 + 时间」，不再发新消息。
3. 同步改测试：`service_test.go:63`、`:140-141` 的断言本来就是按"双发"写的，要一起改，并在注释里写明为什么改。

验收：在飞书里问一句「你现在是什么模型」，**只出现一条消息**，且内容就是答案。

### 第二批（1.5 天，把过程做顺）

4. **流式节流更新**：执行过程中每 1–2 秒刷新卡片（限制：同一卡片一秒最多一次 patch）。
5. **失败可读**：错误分类（网络 / 审批超时 / 工具失败 / 预算耗尽）→ 四句人话 + 重试按钮。
6. **长答案折叠**：超过阈值先给摘要 + 「展开全文」。

### 第二批追加（1 天，群聊 active）

7. **群级三态 + 护栏**：`MentionOnly` 从全局布尔升级成按群的 `off/mention/active`；
   `service.go:421` 改成查群配置；`:461` 的 `join` 按 active 判断。

### 第三批（1 天，补上下文）

7. **飞书历史消息**：拉最近 N 条 + 增量 cursor，落进频道历史，和实时消息同一张表。

## 6. 问题记录 · 应用级提示冗余（2026-11-26）

**现象**：飞书单聊/群聊里，模型常把回复写成"这是一件任务，我来做…"这种派单口吻，正文里带过程话；
同一条消息在提示里被描述两次，上下文预算被白吃。

**根因**：`service.go:80` 定义的 `taskLead`（`这是从飞书来的一件任务…`）在 `:456`（单聊）和 `:463`（群聊）
**每条消息前都拼一次**；而 `loop_backend.go` 的系统提示里已经通过 `if feishuOn { … }` 写了同一句语义。
即：稳定规则写在系统提示是对的，每条再复述一遍是多余的。

**证据**
- `internal/feishu/service.go:80` — `taskLead` 常量定义
- `internal/feishu/service.go:456` / `:463` — 两处拼接点（单聊 / 群聊）
- `internal/agent/loop_backend.go` — `if feishuOn` 分支已含「飞书里的一句是一件任务…回复会写回原来那张卡片」
- `internal/agent/loop_backend.go:479` — 该文件注释自身主张："两边都写一遍等于每轮让模型读两遍同一件事，白占上下文预算"
- `internal/agent/manager.go:1045-1057` — `PromptRequest` 已有 `ChannelID / ChannelName / Context / Images` 结构化字段，够用

**决策**：删除 `taskLead` 及其两处拼接。**不新增**自然语言前缀；来源信息走结构化字段，
"飞书消息是任务、回复回卡片"这条一次性的规则留在系统提示里。

**验收**
- 单聊/群聊回答都写回卡片（不是只吐正文）；
- 正文里不再出现「这是从飞书来的一件任务」；
- 群聊引用历史时仍能正确带上下文（依赖 `Context` 字段，不依赖前缀）。

**风险与兜底**：若无前缀后出现"只写正文不回复"，处理方式是往**系统提示**补一句（进缓存、只读一次），
不回到每条消息前拼字符串。这是两种改法的本质差别：一次性成本 vs 每轮成本。

**工作量**：0.3 人日（含单聊/群聊两场景验证）。
