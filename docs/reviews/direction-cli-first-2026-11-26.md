# 方向：从「舰队」转回「工作台」（CLI 手感优先）

> 2026-11-26 · 分支 `fix/p0-correctness-stopgap` · 基于 HEAD `151779f` + 当日未提交改动
> 证据口径：每条结论都有 `文件:行号` 或截图对应。**仓库当前正被另一个会话并发修改**
> （`verify.go` 11:17 新建、`broker.go` 有改动 + 新测试），下文标注「已在他人手上」的项不要重复做。

## 0. 一句话

你要的不是「更多能力」，是**更少摩擦**。现在这个应用是**舰队优先的骨架**（队列、审批、会话隔离、多视图），
却装着你**CLI 优先的期待**（一句话就跑、目录随便跳、上下文自己会找）。两者错配，所以越用越像负担。
方向应该是：**保留舰队的观测能力，把执行面退回工作台**。

## 1. 四类症状 → 三个结构性错配

### S1 答非所问（截图 1、2）

它说「没读取到 AI review 通知群里的消息，实际拿到的是 multi-agent-desktop 的提交」——这不是模型判错，
是**它能看见的世界只有三样，而且都很窄**：

| 来源 | 现状 | 证据 |
|---|---|---|
| 目录 | 只有会话的 `WorkDir` + 白名单式 `ExtraDirs`；`bash` 的 cwd **恒定**为主目录 | `builtin.RegisterRoots(reg, workDir, extra)` `loop_backend.go:165`；`cmd.Dir = b.WorkDir` `builtin.go:116`；`manager.go:591` 注释自陈「命令在哪跑必须是确定的」 |
| 提示范围 | 系统提示只写一行 `工作目录：X`，**不告诉模型还有哪些项目存在** | `loop_backend.go:459` |
| 渠道 | 单聊历史**刻意**排除频道消息，频道回合也不拼私聊 | UI 自述「群聊内容记录在频道，不进下面的单聊」；既有 `TestChannelTurnPromptExcludesPrivateHistory` |
| 飞书历史 | 只有 `reply` 与 `chats/{id}/members` 两个接口，**没有 list messages** | `feishu/auth.go:86`、`feishu/cred.go:311`；截图 2 里它自己说的「历史消息没集成」与代码一致 |

所以它不是「想偷懒」，是**确实没有那条路**。你说的「在这个目录聊天，也能处理另一个目录」——
现在跨过去也只会被 `workdir.Roots` 挡回来，模型连试的动机都没有。

### S2 频道一套、会话一套（截图 3 vs 1/2）

三个渲染器并存：`AgentView.tsx`（会话：气泡 + agent 头 chips + 模型/路径 chip）、
`ChannelView.tsx`、`FeishuRoomView.tsx`（频道：头像 + 卡片 + 复制/转派）。
**同一个 agent、同一段对话，换个入口就换一套视觉语言和交互**——这是纯认知负担，不产生任何能力。

### S3 慢、被打断、不敢放手

- 消息进 `a.queue`（`manager.go:1810 foldIntoTurn`），不是直接执行；
- 写操作过 `approval.Center` 三档；
- 插话是**两个固定点轮询**（`loop.go:279` / `loop.go:374`），工具执行期间读不到；
- 更糟：模型已给出 3 个工具调用时插话，这 3 个会被**全部判失败**回填假结果（`loop.go:377-381`）。

### 错配总结

| 你的期待（CLI / 编辑器） | 现在的实现（舰队） |
|---|---|
| 一个 shell，`cd` 去哪都行 | 一个会话钉死一个目录，附加目录只读白名单式 |
| 说完就跑，0.5 秒看到输出 | 入队 → 可能被插话打断 → 等审批 → 才跑 |
| 上下文自己找（`rg`、`git log -p`） | 只能看当前渠道的实时消息 + 当前目录 |
| 一个聊天窗口 | 会话 / 频道 / 飞书群 三套界面 |

## 2. 方向判断：一个工作台，不是一支舰队

三条原则，按顺序决定一切：

**① 会话是一个可移动的游标，不是一间锁死的房间。**
目录应该是「当前所在项目 + 可用项目清单」，`cd` 式切换零成本；跨项目读写**默认允许**，
只有真正越界（系统目录、别的用户目录）才拦。这是主流编辑器的做法（Cursor 打开文件夹、VS Code 多根工作区）。

**② 一套消息层，一套渲染。**
渠道（单聊 / 群 / 飞书）只是消息的**属性**（`channelId`），不是另一套界面。
`ChannelView` 应该退役，频道退化成 AgentView 里的一个 thread 视图或一个过滤。

**③ 默认直跑，审批是例外。**
默认 `auto`，只对高危（`rm -rf` 之外的敏感路径、凭据、外发）拦。
现在的 `ask` 默认 + 三档切换，是把「安全」当默认体验，代价是每步一次点击。

### 保留 / 降级 / 删

| 能力 | 处置 | 理由 |
|---|---|---|
| 审批 + audit + shellguard | **保留**，但阈值改成高危 | 这是别人没有的差异化，也是敢自动跑的前提 |
| 舰队视图 / 状态条 | **保留**，降为侧栏 | 观测价值高，不占主交互 |
| Supervisor 自动拆任务 | **默认关**，手动开 | 一句话拆 3 个子会话，对单点任务只是延迟 |
| 网关 / 飞书 | **保留**，作为输入通道 | 已内嵌，边界清楚（`409 CHANNEL_NOT_OWNED`） |
| ChannelView / FeishuRoomView | **合并进 AgentView** | 三套渲染是净成本 |
| 会话级 `ExtraDirs` 白名单 | **升级为工作站 + 项目索引** | 现在的形态解决不了「A 目录聊天、改 B 目录」 |
| verify 工具 | **已在他人手上**（`verify.go` 11:17） | 别重复；核对它与提示词是否一致即可 |
| broker / `gw` 并发修复 | **已在他人手上**（`broker.go` + 新测试） | 别重复 |

## 3. 改造清单（按「改手感」排序，不是按技术难度）

### P0-1 目录变成工作站（不是「喂清单」，是「给腿」）

> 上一版这里写的是「启动扫 gowork 建项目索引注入提示」——**已废弃**。主流 AI code 工具
> （Claude Code / Cursor / Cline）都不这么做：边界由用户显式声明，内容由模型用工具自己查。
> 扫盘注入既烧上下文，又会把无关项目当线索，反而制造答非所问。

1. **`ExtraDirs` 升级为「工作区根」**：`workdir.Roots` 本来就是多根（`roots.go:16`），
   问题是 UI 把它埋在会话设置里、提示词不列、`bash` 钉死主目录。改成显式声明：
   添加文件夹 / 移除文件夹，和编辑器的「打开多个文件夹」同形。
2. **提示词只列用户选过的根**：`工作区根：multi-agent-desktop、data-service`——两三个名字，不是全盘扫描。
   （`loop_backend.go:459` 现在只有一行 `工作目录：X`）
3. **放开移动能力**：
   - `bash` 增加可选 `cwd`（受 roots 校验），不再恒等 `WorkDir`（`builtin.go:116`）；
   - `glob` / `grep` 支持跨根搜索（两者已是 `Writes()=false`，零审批，路已通）；
   - 模型想找邻居，自己跑 `ls ..` / `glob ../**/go.mod` 即可，不需要谁喂清单。
4. **提示词删掉限制性宣示**：`loop_backend.go:475`「文件工具只能碰工作目录和已授权的附加目录」
   改成「工作区根内任意项目可读写，越界会被拦」。

风险：放宽写范围后 shellguard 与审批阈值必须同步收紧，否则一个会话能改坏所有仓库。

### P0-2 消息层统一

- 抽一个 `MessageRow` 组件，三处（会话 / 频道 / 飞书群）共用；
- `ChannelView` 的「复制 / 转派」变成消息 hover 操作，不再需要独立界面；
- 迁移：`agents.json` 里 channel 消息已经在 `Channel.Messages`，渲染层合并即可，不动存储。

### P0-3 插话真打断

把 `Steer` 的拉改成推：ctx 挂 pending 通道，收到即 cancel 当前工具（返回 `Cancelled`），
直接回到下一次模型调用；删掉「整批工具判失败」那段（`loop.go:374-383`）。

### P1-1 飞书历史可拉

接 `GET /open-apis/im/v1/chats/{chat_id}/messages`，一次拉最近 N 条 + 增量 cursor，
落到频道历史（和实时消息同一张表）。这样「昨天的 review 通知」它才看得见。

### P1-2 上下文自动取证

给 `grep`/`glob` 加「跨项目搜索」开关（默认工作站内全项目），
模型问「data-service 的那个 MR 改了哪」时能真去搜，而不是先问你要路径。

### P2 收尾

- 审批默认 `auto`；`ask` 保留为「谨慎模式」；
- Supervisor 默认关；
- 失败恢复三动作（重试 / 换模型 / 放弃）—— 现在失败了只有一条长文字。

## 4. 明确不做

- **不再加第 4 套视图**（看板、时间线、图谱）：视图越多，越认不出同一个东西；
- **不做群聊/单聊两套历史语义**：一套消息表 + `channelId` 字段就够；
- **不追 MCP / 评测集**（等执行手感稳定再说，且有人在动 verify）；
- **不扩 Supervisor 的能力**（它现在的问题不是能力不够，是默认开着）。

---

## 5. 节奏（建议，不承诺工期）

| 阶段 | 内容 | 完成信号 |
|---|---|---|
| 第 1 步 | 项目索引 + cwd 可移动 | 在同一会话里让它改 `data-service` 的一个文件，成功 |
| 第 2 步 | 插话真打断 | 跑 60s bash 时插一句，2 秒内被接管 |
| 第 3 步 | 消息层统一 | 频道和会话长得一样，只有来源标签不同 |
| 第 4 步 | 飞书历史 + 跨项目检索 | 「昨天的群通知」能被自己找到 |
| 第 5 步 | 审批降噪 | 一天下来点「允许」不超过 5 次 |

---

## 6. 一句话结论

**这个项目现在的能力不缺，缺的是「一条顺畅的主路径」。**
把执行面退回工作台（目录自由、一套界面、默认直跑），
把舰队能力（审批、审计、观测、网关）退到「叠加层」——这才是 CLI 手感 + 多 agent 的正确组合。

现在的形态反过来：主路径处处是关卡，叠加层反倒成了主角。
