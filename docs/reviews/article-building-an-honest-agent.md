# 做一个能真的干活的 AI Agent 桌面端，难的不是接模型

> 本文基于 `multi-agent-desktop` 的真实开发记录。所有数字都是本机实测，
> 所有失败案例都有截图或代码行号。包括那些不好看的部分。

## 引子：它说「当前工作环境完全离线」

我让应用里的 agent 评价一个 GitHub 仓库。它回答：

> 我无法访问外部网络或 GitHub 仓库，**当前工作环境完全离线**，所有操作仅限于本地文件系统。

然后它热心地建议：你可以自己 clone 下来，告诉我路径，我帮你读。

我在同一台机器上跑了一下：

```
$ curl -o /dev/null -w "%{http_code}" https://github.com/...
200
```

网络是通的。它有 `web` 工具能开网页，有 `bash` 能跑 `curl`。它甚至没试。

根因在系统提示里的一句话：

```
你只能操作工作目录内的文件。浏览器页面用 web 工具，不经过工作目录。
```

这句话的本意是**文件边界**——防止模型去读 `/etc/passwd`。但模型读成了「整个环境只能碰本地文件」，
于是推断出「离线」。

**模型在只看到约束、没看到许可时，会做最保守的推断。这是合理行为，不是模型笨。**

这是我要讲的第一个诚实：**能力诚实**。你得告诉它什么能做，而不只是什么不能做。

## 一、四种不诚实，四种「变笨」

开发这个项目的过程中，用户（也就是我自己）反复说同一句话：「怎么感觉集成进来之后 agent 变笨了？」

每次查下去，根因都不是模型能力，是产品在某处撒了谎——通常不是故意的。

### 1. 能力不诚实：只写限制，不写许可

上面那个例子。修法是把「只有限制」改成「限制 + 许可」：

```
这台机器可以联网。要看网页、查仓库、拉文档就用 web 或 bash（curl/git clone）。
文件工具只能碰工作目录和已授权的附加目录；这条只管文件，不等于离线。
只有真试过并拿到错误（DNS 失败、连接被拒、超时）才能说访问不了。
bash/写文件可能要等用户批准。等不到批准不等于没这个能力。
```

最后一条尤其重要。原来 agent 想开网页时卡在审批上，等不到批准，
就把「审批没通过」归因成「环境不允许」。这两件事必须分开说。

顺带发现 `web` 工具被标成了写操作（`Writes() = true`），
意味着**每次查资料都要弹一张审批卡**。查网页不产生本地副作用，改成只读后这个摩擦直接消失。

### 2. 记忆不诚实：压缩就是丢掉

用户问：「你还知道上次需要处理什么吗？」

agent 列出了三条待办，带精确行号、函数名、文件路径。看起来非常可信。

**三条全是编的。** 那个会话里根本没有这些待办。

它的思考过程被记录下来了：「摘要被截断」「候选：1... 2... 3... 4...」——
它在逐个列举候选然后挑一个。这是典型的不确定时的编造。

为什么会这样？因为上一轮它被预算砍断了：

```
预算用尽: iteration limit reached (24/24)
```

而当时的代码里，**预算耗尽这条路径不跑摘要沉淀**。正常结束会写摘要，被砍断不会。
所以下一轮它手上是空的，但提示词暗示它「应该有摘要」，于是它拿当前工作目录的代码知识缝合出了答案。

更深一层的问题在压缩函数本身。它长这样：

```go
b.WriteString("用户: " + oneLine(m.Content, 120))
b.WriteString("回复: " + oneLine(m.Content, 120))
```

**本地字符串截断。** 丢掉的内容真的没了，只剩每句话的前 120 字。

对照 pi 的做法：压缩时**真的发一次模型请求**，产出结构化摘要
（目标 / 约束 / 进度 / 决定 / 下一步 / 关键上下文），存进检查点，
下次压缩从保留边界继续迭代。

改法不复杂，因为项目里已经有一条真调模型的摘要管道（学习助手），
只是它和压缩函数各干各的、互不相认。把两条接成一条就行。

这是第二个诚实：**记忆诚实**。压缩要么真写摘要，要么明确告诉模型「这段没了，不知道就说不知道」。
最差的做法是假装还有记忆。

### 3. 身份不诚实：它不知道自己是谁

用户让 agent「整理一下你的子 agent」。它回答：

> 我（前端 5）当前没有任何子 agent。

但用户是在**「测试工程师」**这个会话里问的，而侧栏树明明显示测试工程师有 6 个子会话。

查数据：树是对的，agent 认错了自己。

根因：**系统提示从来没告诉 agent 它的名字和 ID**。
`list_agents` 工具也只返回「名字 · 角色」，不标哪个是自己。
17 个会话里，它只能从历史对话里猜——猜错了。

修法两行：

```
你是「测试工程师」（id agent-...089000）。
list_agents 里名字和你相同的才是你，不要把自己当成历史里出现过的别的名字。
```

加上 `list_agents` 在自己那行标 `← 这是你自己`。

第三个诚实：**身份诚实**。多 agent 系统里，「我是谁」必须显式给定，不能靠推断。

### 4. 状态不诚实：界面说「已就绪」，其实什么都没配

这一条是做 UX 审计时发现的，也是最严重的。

我用 Playwright 驱动真实界面，模拟一个第一次打开产品的用户：
新建会话 → 进入对话 → 输入一句话 → 点发送。

同一屏上的矛盾：

- 主区大字：**「我的第一个助手 已就绪」**
- 侧栏小字：「未选模型和文件夹」
- 底栏：「选择模型」「未设置」

实测输出：

```
SEND_DISABLED= false
CALLS= [..., "API.PromptAgent"]
```

**发送按钮可点，而且真的发出去了。** 用户信了那句「已就绪」，
发完消息，然后没有回答、没有报错、状态还是「空闲」。

再往上追，新建对话框里**根本没有模型这一项**，文件夹也不是必填：

```
CREATE_DISABLED_NO_FOLDER= false
CREATE_CALLS= [{"method":"API.CreateCLIAgent","args":["前端","React / TypeScript 专家…","loop"]}]
```

注意参数里没有 workDir。

而对话框里第一个要用户决策的，是「运行时：原生 / 进程内 loop vs 外部 ACP」。
**问了最不重要的，漏了最必需的。**

还有一个更隐蔽的：出错时界面只显示右上一个「出错」红标，**原因一个字都没有**。
我构造了一个 `lastError: '这个会话还没有模型'` 的会话——数据里有，屏幕上没有。

```
$ grep lastError src/lib/useBackend.ts
（零命中）
```

后端下发的错误原因，前端从未读取。只有错误事件活着时才显示，
切会话或重启后就变成无法诊断的黑盒。

第四个诚实：**状态诚实**。界面说的每一句「就绪」「完成」「成功」，
都必须能被当前真实状态支撑。

## 二、一个反直觉的成本发现：减提示词省下的，被加工具吃回去了

用户抱怨「感觉全是提示词」。我实测了一下，确实严重：

| 项 | token |
|---|---|
| 系统提示 | 1385 |
| 15 个工具的 schema | 2507 |
| **固定开销** | **3892** |
| 预算 | 8000 |
| **真正留给对话** | **4108** |

**每轮请求里，一半的 token 花在「告诉模型它是谁、能干什么」。**

而且系统提示里那 9 条工具说明，和工具自己的 `Description()` 是重复的——
模型每轮读两遍同样的内容。

于是做了一轮减负：工具说明全部移到工具自己的描述里，
系统提示只留 schema 塞不下的跨工具规则。知识注入从「塞正文」改成「只给标题目录」。

效果很好：

- 系统提示 1385 → 485 token
- 12 条知识笔记：4375 → 99 token（正文靠 `list_notes <query>` 现查）
- 固定开销 3892 → 2899

**然后加了几个工具，成本回去了。**

这是今天重测的数字：

| 项 | token |
|---|---|
| 系统提示 | 532（静态 489 + 动态 43） |
| **18 个工具的 schema** | **3525** |
| **固定开销** | **4057** |

工具从 15 个加到 18 个（`grep`、`glob`、`apply_patch`、`verify`、`invite_to_channel`），
schema 成本从 2414 涨到 3525。

**现在工具 schema 占固定开销的 87%。系统提示已经不是主要成本了。**

更值得注意的是：预算计算是这样的——

```go
const recent = 8000
const summary = 400
n := sys + recent + summary
```

`sys` 是系统提示。**工具 schema 不进这个预算。**
那 3525 token 每轮都发给模型，却不在预算账本上。

这个发现指向一个明确的结论：**提示词瘦身的收益是有上限的，真正的成本驱动是「工具数量 × schema 啰嗦程度」。**

所以行业往 MCP 走是对的——不是因为它标准化，而是因为**按需发现工具**才能把这块成本从「每轮固定」变成「用到才付」。
把 20 个工具的完整 schema 每轮都塞进去，本质上和「把整个知识库每轮都注入」是同一个错误。

顺带说，项目里已经把系统提示拆成了静态段和动态段（489 + 43）。
这是为 prompt 缓存命中做的——静态段不变，缓存才有意义。这类细节比「精简提示词」更值钱。

## 三、几个安全上的教训

### 正则黑名单是打不完的补丁

项目里有个 `shellguard`，用 9 条正则挡危险命令。它的注释很诚实：

> 这不是沙箱，也不可能覆盖所有变体。

我实测了 12 条危险命令：

```
blocked=true   rm -rf /
blocked=false  rm -rf $HOME
blocked=false  rm -rf ${HOME}
blocked=false  find / -delete
blocked=false  chmod -R 000 ~
blocked=false  python3 -c "import shutil; shutil.rmtree('/Users/...')"
blocked=true   :(){ :|:& };:
```

**12 条里放过 9 条。** `rm -rf $HOME` 都不挡。

修法不是加更多正则，而是加一层**目标解析**：
把 `$HOME`、`${HOME}`、`~`、`$VAR` 展开成真实绝对路径，再判断这个路径是不是「根 / 系统目录 / 家目录本身」。

关键是只拦敏感目录**本身**，相对路径和目录内的子目录一律放行。
这样 `rm -rf node_modules`、`git clean -fd`、`rm -rf ~/Documents/myproj` 都不误伤。

顺带修了一个真实的过度拦截：原正则 `rm -rf ~/...` 是前缀匹配，
把 `~/Documents/gowork/tmp` 这种正常工作目录也拦了——**用户的目录删不掉**。

安全设计里，误杀正常操作比漏杀更糟，因为它会让用户关掉整个防护。

### 「以后都允许」不能是工具级的

原来的审批记忆是 `map[agentID]map[toolName]bool`。
用户对一条 `git status` 点了「本会话允许 bash」，**`rm -rf` 也一起放行了**。

现在的做法比一刀切「bash 永不 remember」更细：**命令族签名**。

```go
var subcommandTools = map[string]bool{
    "git": true, "go": true, "npm": true, "docker": true, "kubectl": true, ...
}
```

取到第二个 token 才够细——记住 `git status` 不会把 `git push` 一并放过。
解析不出签名的 bash 不入记忆、仍走询问。

而且 bash 被单列高危：**自动模式也不放行 bash**，只有文件编辑类享受自动。

### 一个直接越权的洞

飞书审批卡的回调函数：

```go
func (s *Service) decide(cfg Config, t Turn) {
    card := s.takeAsk(t.ActionID)
    allow := t.Action == "once" || t.Action == "keep"
    ...
    s.hooks.Decide(t.ActionID, allow, t.Action == "keep")
}
```

全函数只读 `ActionID` 和 `Action`。**`t.Sender` 从未参与判断。**

后果：飞书群里任何能看到这张卡的人，都能点「允许」，放开本机的文件写入和命令执行。
点「本会话允许」还会长期生效。

这条已修（校验 owner / 白名单）。但值得写出来，因为它揭示一个模式：
**审批 UI 做得越完善，越容易忘记「谁有权点」这个最基础的问题。**

## 四、一个 agent 报告了 7 条结论，4 条是错的

这件事我认为比任何技术细节都重要。

我让应用里的 agent 分析项目缺失的能力。它给了一份格式漂亮的报告：

> ✅ 已确认的最新改动（基于你提供的上下文 + 当前目录结构 + 知识库）
> 关键缺失能力（**已验证、非推测**）

七条，每条都带表格、带「根据来源」。核实结果：

| 它的结论 | 实际 |
|---|---|
| `delete_agent` 未注册为工具 | ❌ 已注册（`loop_backend.go` 的 `reg.Register(&deleteAgentTool{...})`） |
| 审批门 Approver 恒为 nil | ❌ 已接（`main.go` 有 `mgr.SetApprovals(approval.New(...))`） |
| Agent 重命名缺失 | ❌ `set_profile` 就支持改名 |
| delegate 可无限建子会话 | ❌ 有三层上限 |
| 没有全局并发上限 | ✅ 对 |
| bash 不是沙箱 | ✅ 对 |
| 父上下文不注入 delegate | ✅ 对，但**这是故意的**（净室上下文） |

**错的 4 条，恰好是它语气最肯定的 4 条。**

它错在：拿「我在 `builtin.Register` 里没看到」当结论。但那不是工具注册的地方。

这为什么重要？因为**你会靠 agent 的分析来决策**。
如果它 50% 准确率还带「已验证」标签，你会一直修不存在的问题——我自己就差点去修那个「未注册的 delete_agent」。

后来同类事情又发生了两次：

- 一份「能力差距分析」说「没有 grep、没有 glob」，而它们已经存在且是只读的
- 同一份说「每条 grep 都要弹审批卡」，而 `Writes()` 明明返回 false

所以我在项目里加了一条提示词：

```
不确定项目约定、术语或以前的结论时，先 list_notes 查，不要凭印象断言。
```

以及给系统提示补了身份、边界、以及「等不到批准不等于没这个能力」。

**但这些都不够。** 真正的解法是让「结论必须附可验证证据」成为结构约束，
而不是一句劝告。这也是为什么后来那份 UX 审计我坚持要真实截图 + 控制台输出，
而不是读代码推断——并且明确标出哪些是「待验证」。

## 五、协议分层：唯一做对了没返工的部分

项目里现在有四层协议，边界清楚：

| 层 | 协议 | 用途 |
|---|---|---|
| 桌面 ↔ Agent 运行时 | `mad.runtime/1`（自有） | 统一事件、统一生命周期、可替换执行体 |
| ↔ 外部 Agent 进程 | ACP / JSON-RPC 2.0 | 接 grok / codex-acp 等 |
| 前端 ↔ Go | mygo 绑定 RPC | 生成式 typed IPC |
| ↔ 外部渠道 | HTTP + SSE | 内嵌网关 |

`mad.runtime/1` 只定义 12 种事件（`turn.started` / `text.delta` / `tool.finished` / `permission.request` …），
两条兼容性硬规则：

- 版本只升不降，未知字段必须忽略
- **未知事件类型降级为 notice，不丢弃**

第二条是关键。对端升级后多出一种事件，我们仍然能把信息显示出来，而不是断开连接。

还有一个细节值得学：`ConcurrencySafe()` 是**显式 opt-in，默认 false**。
工具不声明就串行。这样新增工具不会因为忘记考虑并发而引入竞态——**默认值是安全的那个**。

顺便澄清一个容易混的概念：**ACP ≠ MCP**。
前者接外部 agent 进程，后者接工具 server。项目有 ACP，还没有 MCP。两者互补。

## 六、诚实的结论：功能完成度高的工程原型

把上面所有东西放在一起，得到一个不太好听但准确的判断：

**后端能力扎实，用户侧缺一条「从打开到第一次成功」的路。**

后端有：多运行时、命令族签名审批、并行只读工具、verify 闭环、内嵌网关、跨会话记忆、计划调度、
git worktree 隔离、多根工作区。这些都是真做出来的，有测试。

但 UX 审计的结论是：

- 新用户第一个核心任务 **100% 失败**（未配置仍可发送）
- 失败后 **无法自救**（错误原因不显示）
- 首屏 **不知道产品干什么**（只有「组建你的 agent 舰队」）
- 「助手」分组点进去是架构文档（「作为库内嵌在桌面主进程中」「未装配、初始化失败」）

**问题不是能力不够，是用户走不到用得上这些能力的地方。**

如果只能改五个地方：

1. 发送前置校验（缺模型/目录时禁用并说明缺什么）
2. 空状态标题诚实化（「已就绪」→ 真实缺失项 + 一键直达）
3. 创建流程必填模型与文件夹
4. 显示错误原因
5. 首屏一句人话定位

这五条全在前端状态装配与校验层，不碰后端契约，成本远低于新增任何一个能力。

**在第一次成功率修好之前，继续新增能力的边际收益接近零。**

## 收尾：一个可以带走的判断

做 AI agent 产品，很容易把精力全放在「能力」上——
加工具、加记忆、加渠道、加并行、加协议。因为这些看得见、可量化、写进 changelog 好看。

但用户的体感不由能力决定，由**诚实**决定：

- 你说能联网，它就得真能联网（能力诚实）
- 你说记得，就得真记得，不记得要说不知道（记忆诚实）
- 你说它是谁，它就得是谁（身份诚实）
- 你说已就绪，就得真能跑（状态诚实）

四种不诚实，用户都会翻译成同一句话：**「这个 agent 好笨」**。

而每一次「变笨」的排查，最后都指向产品某处说了假话——
通常不是故意的，是开发者自己早就配好了环境、早就知道概念、早就看过日志，
于是忘了用户什么都不知道。

**这不是模型问题，是产品问题。而产品问题只能靠产品方法解决：真实跑一遍，站在第一次使用的人的位置上看。**
