## 1. 产品体验总体评价

**当前成熟度：功能完成度高的工程原型，不是可交付给新用户的工具。**

后端能力扎实（多运行时、审批签名、并行只读工具、verify 闭环、网关、记忆、调度），
但**用户侧缺少一条「从打开到第一次成功」的路**。

核心矛盾一句话：**产品处处告诉用户「已就绪」，而实际上什么都没配好。**

这不是缺功能，是**状态诚实性**问题。用户第一次发消息必然失败，且失败后看不到原因。
一个能跑通全部功能的开发者不会遇到这些，因为他早就配好了模型和目录。

## 2. 首次使用体验报告

实测路径（截图 A1 → A2 → C2 → A3 → B1）：

| 步 | 用户看到 | 用户会想 | 实际后果 |
|---|---|---|---|
| 1 | 标题只有「Agent」，主区「组建你的 agent 舰队」 | 这是什么产品？舰队是什么？ | 无任何一句话说明产品做什么 |
| 2 | 顶栏「网关 未启用 / 运行中 0 / 待审批 0 / 队列 0」 | 未启用是不是出错了？ | 正常态被显示成异常态 |
| 3 | 点「新建 Agent」，**第一个要选的是「运行时：原生/进程内 loop vs 外部 ACP」** | loop 是什么？ACP 是什么？ | 实现细节当成用户首要决策 |
| 4 | 选角色、填名字，文件夹看着可选，**没有模型这一项** | 应该好了吧 | 「创建」可点（实测 `CREATE_DISABLED_NO_FOLDER=false`） |
| 5 | 进入会话，主区大字「**我的第一个助手 已就绪**」 | 可以开始了 | 侧栏同时写「未选模型和文件夹」 |
| 6 | 点示例「这个模块有什么风险？」或自己输入 | 它会回答 | **发送可点**（实测 `SEND_DISABLED=false`），真的调用 `API.PromptAgent` |
| 7 | 消息气泡出现，然后…… | 它在想吗？坏了吗？ | 状态仍「空闲」，无报错、无加载态（mock 边界，真实提示待验证） |

**结论：新用户无法独立完成第一个核心任务。** 阻塞点不在操作难度，在于产品没有告诉他缺什么。

## 3. 核心任务体验报告

### 任务 A：让 AI 帮我看一个项目（最核心）

- **用户目标**：说一句话，得到关于我项目的回答
- **用户预期**：打开 → 选目录 → 说话 → 有回答
- **实际路径**：打开 → 新建（先选运行时）→ 创建（无模型无目录）→ 看到「已就绪」→ 发送 → 无结果
- **障碍**：模型配置不在创建流程里；文件夹非必填；发送不做前置校验
- **是否完成**：❌ 未完成
- **改进**：创建流程内嵌模型+目录必填；未配齐时发送禁用并说明缺什么

### 任务 B：搞清楚为什么失败

- **用户目标**：知道错在哪、怎么修
- **实际路径**：看到右上「出错」红标 → 找遍界面无原因
- **证据**：mock 里 `lastError: '这个会话还没有模型'` 已下发；截图 B7 全屏幕无此文案。
  `grep lastError src/lib/useBackend.ts` → **零命中**，后端错误原因从未被前端读取。
- **是否完成**：❌ 未完成
- **改进**：把 `lastError`  seed 进 errors 状态，在会话内显示原因 + 修复入口

### 任务 C：配置模型

- **用户目标**：把模型接上
- **实际路径**：模型弹层提示「到设置的『连接』里保存后再选」（纯文本，不可点）→ 自己找齿轮 → 设置**默认落在「外观」** → 再点「连接」
- **是否完成**：⚠️ 能完成，但多绕 3 步且全靠猜
- **改进**：提示做成可点直达；无模型时设置默认开「连接」

### 任务 D：看多个 agent 在干什么

- **用户目标**：一眼看到谁在忙、忙什么
- **实际路径**：舰队视图并排卡片，状态/耗时/字数齐全
- **是否完成**：✅ **完成，这是产品做得最好的部分**
- 备注：空转卡片文案「打开对话交一句任务，它就开工」仍在承诺无法兑现的事

### 任务 E：小窗口使用

- **实测**：1024×700 与 860×640 均无横向溢出，舰队卡片可读
- **是否完成**：✅ 完成

## 4. 问题清单

### P0 · 阻断性

#### UX-001
**问题名称**：未配模型/文件夹时「发送」可点，主区还宣称「已就绪」
**问题等级**：P0
**问题所在**：AgentView 空状态 + 输入栏发送按钮
**用户场景**：新用户建完第一个会话，直接说话
**用户真实感受**：「它说已就绪，我发了，然后没反应。是我不会用还是坏了？」→ 怀疑产品不可靠
**问题根因**：发送按钮的 disabled 只判连接与输入非空，不判会话是否具备模型+目录；空状态文案写死「已就绪」，与实际配置无关
**实际影响**：第一个核心任务 100% 失败。信任在第一次交互就崩
**证据**：`SEND_DISABLED= false`；调用日志含 `API.PromptAgent`；截图 A3 主区「已就绪」与侧栏「未选模型和文件夹」同屏矛盾
**优化方案**：① 空状态标题按真实配置渲染（缺模型→「还差一个模型」）② 发送 disabled 且 hover 说明缺什么 ③ 缺失项做成一键直达
**验收标准**：零配置新会话中，发送按钮不可点，界面明确列出缺失项并可点击跳转；配齐后立即可点

#### UX-002
**问题名称**：新建会话不含模型选择，且不选文件夹也能创建
**问题等级**：P0
**问题所在**：新建 Agent 对话框
**用户场景**：第一次创建会话
**用户真实感受**：「填完名字点了创建，应该好了」→ 得到一个不能工作的会话
**问题根因**：对话框只收运行时/角色/名称/文件夹，模型不在其中；文件夹无必填校验
**实际影响**：批量生产不可用会话。用户建的越多，坏会话越多
**证据**：`CREATE_DISABLED_NO_FOLDER= false`；实际调用 `API.CreateCLIAgent("前端", "React / TypeScript 专家…", "loop")` —— **参数里没有 workDir**
**优化方案**：模型与文件夹设为必填并就地可选；未填齐时「创建」禁用并标出缺哪项；预览区的「就绪」改为真实校验结果
**验收标准**：不选模型或文件夹时无法创建；预览区状态与实际配置一致

### P1 · 严重体验问题

#### UX-003
**问题名称**：会话出错只显示「出错」，原因完全不可见
**问题等级**：P1
**问题所在**：AgentView 错误态 / useBackend 错误状态装配
**用户场景**：切到一个之前失败过的会话，或重启后回看
**用户真实感受**：「红了，但为什么？我该改什么？」→ 只能瞎试或放弃
**问题根因**：错误原因只在 `agent.error` 事件活着时进 state；后端 AgentView 的 `lastError` 字段前端从不读取
**实际影响**：任何非实时错误都变成无法诊断的黑盒，直接推高放弃率
**证据**：截图 B7（`lastError` 已下发，界面无该文案）；`grep lastError src/lib/useBackend.ts` 零命中
**优化方案**：加载会话时用 `lastError` 初始化 errors；在会话内渲染原因横幅 + 对应修复入口
**验收标准**：构造一个 `lastError` 非空的会话，切进去能看到原因原文与修复按钮

#### UX-004
**问题名称**：设置默认落在「外观」，最需要配的「连接」排在第二
**问题等级**：P1
**问题所在**：设置弹窗默认 tab
**用户场景**：新用户被提示「去设置的连接里保存」后打开设置
**用户真实感受**：「让我配模型，怎么给我看主题？」
**问题根因**：默认 tab 硬编码为外观，不感知「当前有没有可用模型」
**实际影响**：核心配置路径多绕一步，且与引导文案不符
**证据**：截图 A6，设置打开即「外观/主题」，连接在左侧第二项
**优化方案**：无已配置模型时默认打开「连接」；否则保持外观
**验收标准**：零模型状态下打开设置，首屏即连接页

#### UX-005
**问题名称**：首屏没有任何产品定位说明
**问题等级**：P1
**问题所在**：舰队空状态 / 应用标题
**用户场景**：第一次打开
**用户真实感受**：「Agent 是什么？舰队是什么？这东西帮我干什么？」
**问题根因**：文案面向已理解概念的开发者（「组建你的 agent 舰队」），没有一句话价值说明
**实际影响**：用户无法判断这产品是否解决自己的问题，直接影响留存
**证据**：截图 A1，全屏无一句说明产品用途
**优化方案**：主区加一句人话定位（例：「让几个 AI 助手同时读你的代码、改你的项目」），并给一个「先接一个模型」的起步按钮
**验收标准**：新用户在首屏 5 秒内能说出产品做什么、下一步点什么

#### UX-006
**问题名称**：「助手」分组里放的是基础设施，页面文案是架构文档
**问题等级**：P1
**问题所在**：侧栏「助手」分组 → 网关 / 记忆 / 计划
**用户场景**：新用户想找「更多助手」，点进去
**用户真实感受**：「说是助手，怎么在讲主进程和装配？我要做什么？」
**问题根因**：分组命名与内容不符；空状态直接展示内部实现说明（「作为库内嵌在桌面主进程中」「未装配、初始化失败」「本地 Hub」「独立常驻服务是后续形态」）
**实际影响**：三个一级入口对普通用户零价值，且制造「这产品不是给我用的」印象
**证据**：截图 B6-网关 / B6-记忆，正文均为架构描述，无用户可执行动作
**优化方案**：① 分组改名（如「自动化」/「后台」）② 空状态改成用户语言 + 一个动作 ③ 架构说明收进「关于/诊断」
**验收标准**：三个页面各自有一句用户能懂的用途说明和至少一个可执行动作

#### UX-007
**问题名称**：示例问题在不可用状态下仍可点，主动把用户引向失败
**问题等级**：P1
**问题所在**：AgentView 空状态示例按钮
**用户场景**：新用户看到「这个模块有什么风险？」觉得省事就点了
**用户真实感受**：「它自己给的例子都跑不通」
**问题根因**：示例按钮不判会话可用性
**实际影响**：产品主动引导的失败比用户自发的失败更伤信任
**证据**：截图 A3/B1/C1 三屏中示例按钮均在无模型状态下正常呈现
**优化方案**：未配齐时示例置灰或替换为「先选模型」引导
**验收标准**：零配置状态下点不到会失败的示例

### P2 · 一般体验问题

#### UX-008
**问题名称**：空状态引导文字对比度不达 WCAG AA
**问题等级**：P2
**问题所在**：全局 `--text-tertiary` / `--text-disabled` 用于引导文案
**用户场景**：光线较亮或视力一般的用户读空状态指引
**用户真实感受**：「灰蒙蒙的，看不清写的什么」
**问题根因**：把「次要信息」的色阶用在了「唯一引导信息」上
**实际影响**：关键引导读不到，等于没有引导
**证据**：实测计算（暗色 `--bg-base: #0a0c10`）：`--text-tertiary #6e7789` = **4.35:1**（AA 需 4.5）；`--text-disabled #454d5c` = **2.30:1**
**优化方案**：引导性文案至少用 `--text-secondary`（8.66:1）；disabled 色只用于真正不可交互元素
**验收标准**：所有空状态引导文案对比度 ≥ 4.5:1

#### UX-009
**问题名称**：新建对话框把「运行时」放在第一位
**问题等级**：P2
**问题所在**：新建 Agent 对话框首个字段
**用户场景**：第一次创建
**用户真实感受**：「进程内 loop？外部 ACP？我不知道选哪个，默认那个吧」
**问题根因**：实现分层直接暴露成用户决策
**优化方案**：默认 native 并折叠进「高级」；主流程只留角色/名称/模型/文件夹
**验收标准**：默认路径不需要理解运行时概念即可创建

#### UX-010
**问题名称**：首屏四个创建入口，语义重叠
**问题等级**：P2
**问题所在**：侧栏「+ 新建 Agent」、主区三个角色按钮、「自定义名称与角色 →」、侧栏「自动拆任务」
**用户真实感受**：「都像是新建，有什么区别？该点哪个？」
**问题根因**：快捷入口与完整入口并列，未区分主次
**优化方案**：主区保留一个主 CTA + 角色快捷；「自动拆任务」移出首屏或加一句区别说明
**验收标准**：首屏只有一个视觉主 CTA

#### UX-011
**问题名称**：顶栏四个计数器全 0，且「网关 未启用」形似报错
**问题等级**：P2
**问题所在**：顶部状态条
**用户场景**：首次打开
**用户真实感受**：「未启用？是不是我装错了」
**问题根因**：把运行态监控常驻在首屏，且正常态用了警示措辞
**优化方案**：零会话时隐藏计数器；「未启用」改中性表述或收进诊断
**验收标准**：首屏不出现让用户误判为故障的措辞

#### UX-012
**问题名称**：空模型弹层只给纯文本指引，不可点击
**问题等级**：P2
**问题所在**：模型选择弹层空态
**用户真实感受**：「让我去设置的连接，那我得自己找」
**证据**：截图 C1，文案「没有已配置的模型。到设置的『连接』里保存后再选。」为纯文本
**优化方案**：改为按钮，直接打开设置的连接页
**验收标准**：从空模型弹层一次点击到达连接配置

#### UX-013
**问题名称**：角色描述是提示词片段，不是用户价值说明
**问题等级**：P2
**问题所在**：新建对话框角色卡片
**用户真实感受**：「边界条件·异常路径·复现步骤 —— 这是给我看的还是给模型看的？」
**证据**：截图 A2，五个角色描述均为关键词串
**优化方案**：改成「它擅长帮你做什么」的一句话
**验收标准**：用户能据描述判断该选哪个角色

## 6. 产品体验改进路线图

### 第一阶段 · 必须立即解决（让第一个任务能成功）

## 7. 最终结论

**这个产品目前是否真正适合用户使用？**
对**已配好环境的开发者**：适合，舰队视图和审批治理是真实优势。
对**新用户**：不适合。第一个核心任务无法独立完成，且失败后无法自救。

**用户最容易在哪些地方放弃？**
1. 发第一条消息没反应（UX-001）
2. 看到「出错」但找不到原因（UX-003）
3. 首屏不知道这产品干什么（UX-005）
4. 点「助手」看到主进程/装配等术语（UX-006）

**哪些设计最不符合用户直觉？**
- 「已就绪」与实际配置无关（状态不诚实）
- 创建流程不问模型，却把运行时放第一位（问了不重要的，漏了必需的）
- 出错只给红标不给原因
- 空状态用架构文档当用户文案

**哪些问题最值得优先投入开发资源？**
UX-001 / UX-002 / UX-003 三条。它们共同构成「第一次能不能成功」，
且改动都在前端状态装配与校验层，不碰后端契约，成本远低于新增能力。

**如果只能修改 5 个地方：**
1. **发送前置校验**：缺模型/文件夹时禁用发送并说明缺什么（UX-001）
2. **空状态标题诚实化**：把「已就绪」换成真实缺失项 + 一键直达（UX-001）
3. **创建流程必填模型与文件夹**（UX-002）
4. **显示 `lastError` 原因**（UX-003）
5. **首屏一句人话定位 + 起步按钮**（UX-005）

这五条做完，新用户从「必然失败且不知为何」变成「知道缺什么、点一下就能补上」。
**在此之前，继续新增能力的边际收益接近零** —— 用户还没走到用得上那些能力的地方。
