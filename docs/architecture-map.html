值得注意的几条边

  • llm → tool：provider 适配层只需要工具的 Spec 来描述函数，不反向依赖注册表。
  • loop → llm, tool：循环只认一个更窄的 Model 接口（给历史，拿一轮结果），流式解析留在 provider 层。
  • agent 不依赖 mygo：它持有的只是一个 Emitter 函数，单测时可以换成收集事件的实现。
  • tool → browser, proc, workdir：内置浏览器、进程组和目录校验都是工具的真实外部边界。

分层纪律

  • 依赖方向恒为 main ← 业务 ← 基础设施；底层包不 import UI 层，所以事件类型各自定义，不互相复用。
  • channel.DecideReplies 是「谁该回」的唯一判定，绑定层只投递，不重复实现规则。
  • 跨 goroutine 的返回值必须是副本（clone()），不泄漏内部指针。
  • 新增事件必须同时有前端订阅，否则 TestEveryBackendEventIsSubscribed 会失败。

05

执行循环：把四个控制点插在每一次迭代之间

委托给外部 CLI 时，「停止生效、结果结构化、预算可控、可中途干预」这四个控制点全部拿不回来——因为委托模式里根本没有「迭代」这个位置。 loop.Runner 存在的理由，就是在进程内把这个位置造出来。

01 / loop.go:243 最前面
停止信号

先看 runCtx.Err()。任何阶段被打断都立刻进入 PhaseStopped，写 stopReason、落检查点再返回。停止按钮不再「看起来生效但进程还在跑」。

02 / loop.go:257 只增不减
预算检查

Budget.Exhausted() 依次判断轮次、工具次数、墙钟。只存已用量不存剩余量，所以暂停 / 恢复不会把额度重置。超了就是 PhaseBudget。

03 / loop.go:265 Steer
插入用户插话

每次问模型之前，把后到的本会话消息取出来 append 进这一轮，而不是等整轮结束。群消息不进这条路径，留到这一轮结束再入队。

04 / loop.go:272 iter.start
轮次开始与上下文占用

迭代计数 +1，进入 PhaseThinking，同时发出 ctxUsed / ctxBudget / ctxLimit。三个值必须由后端算——前端自算不含 system 与内部 tool 轮次，必然偏小。

05 / loop.go:288 顺序有讲究
检查点必须在模型调用之前

模型调用是最贵的一步。在它之后落盘，意味着崩溃时钱已经白花了。Sync 顺便把完整消息拷回会话，避免只在整轮结束才写盘。

06 / loop.go:292 最多重试 4 次
收窗口，再调模型

发出前先 llm.Compact 裁到约 8000 token（system 原文另算）。服务端仍报装不下，就把预算减半重来，下限 512，最多 4 次，而不是直接失败。

07 / loop.go:337 终止条件
记录这一轮说了什么

assistant 的正文、推理与 toolCalls 一起进历史。没有工具调用就等于任务结束：PhaseDone + FinalText。工具回合留在历史里给模型看，但不逐条冒到界面。

08 / loop.go:373 逐个串行
执行工具

每个调用先计预算、发 tool.start，再进注册表：schema 校验 → 指纹去重（同参第 3 次直接拦下）→ 可选 Approver → 超时 → 头尾各半截断。结果以 tool 消息回填。

09 / loop.go:359 用户优先
中途插话 = 放弃本批工具

模型这一轮已经排好的工具调用全部不执行，逐个回填「这步先不做：用户插了一句」。把新说明 append 进历史后继续下一轮，让用户的话直接改变方向。

10 / loop.go:400 防打转
连续无进展就终止

连续 3 轮既没有成功的工具调用、也没有最终答案，判定原地绕圈，PhaseFailed。再跑下去只是烧预算。

11 / 结局四种 返回值永远是状态
done · stopped · budget_exhausted · failed

治理层的失败（超预算、被打转拦截）是正常结局，不是异常。真正的 error 只保留给「跑不下去了」，比如模型调用本身不可用。

默认预算（第一次跑不至于烧穿钱包）

24 轮
MaxIterations
64 次
MaxToolCalls
600 秒
MaxWallMS（暂停时长不计入）

提示词预算开跑后按模型窗口推导；超了先压缩，不直接停。检查点跟检查点节奏走，不按 token 落盘。

会话状态机

idle→ 入队 → queued→ worker 取到 → running→ 结束 → idle /error
running或queued → BlockAgent →blocked → Unblock →idle

一轮正常结束调用 setIdleOrQueued：队列空则 idle，还有消息则 queued。不会停在 done，也不留一颗绿色的「完成」点。

06

工具与模型：循环真正能伸出去的手

每个会话在开跑前才装配工具（tool.NewRegistry()），而不是全局注册一份。文件读写与 bash 被限制在该会话的工作目录内。

工具来源能力行为与边界
read_filebuiltin只读只碰工作目录内的文件，先读再改是系统提示的第一条规则。
write_filebuiltin写直接执行，正式注册表上没有审批闸门（Approver 为空）。
edit_filebuiltin写oldText 必须与原文完全一致（含缩进）且只出现一次，否则报错让模型自己改。
bashbuiltin执行默认 60 秒，超时杀整个进程组；不读登录脚本；stdout/stderr 整段返回，不流式。
list_agents会话读看现在有哪些会话、各自在做什么。
ask_agent会话协作按名字把任务交给已有会话并等回复。互相等待会被拦住，避免死锁。
create_agent会话协作新建助手，沿用同一模型与工作目录；带 task 时会等它做完；ParentID 记父子关系。
delete_agent会话写只能删自己，或自己创建的子会话。
list_notes知识读看知识库已有笔记。
save_note知识写写一条并挂到自己身上，下一轮进系统提示。禁止直接改 knowledge.jsonl。
set_profile会话写改自己的名字、简介或工作目录，简介用来记住当前负责什么。
webtool/web网络操作内置浏览器：按控件编号或页面可见文字，一次最多 12 步，只交回最后一页。

数据与事件：状态落在哪，界面怎么知道

全部持久化都在用户数据目录（%APPDATA%\multi-agent-desktop / ~/Library/Application Support / $XDG_DATA_HOME）。 agents.json 是完整历史，界面只拿当前会话最近一页。
